# 读需求文档并生成功能点

把「需求文档」变成「可派给人、可勾完成的功能点」。这份 skill 的难点不在读字，而在三件事：
**判断文档是哪种形态**、**认出文档自己约定的变更标记**、**把没写的和写过的分开**。

---

## 1. 铁律（动手前先读完这一节）

1. **不要只读解析出来的 `.txt`。** `.docx` 的底色、加粗、修订标记在解析成纯文本时就丢了。
   本工作区的解析器（`dsh-client-ui-workbench/lib/client.js` 的 `wordXmlToText`）只取文本节点，
   明确丢弃 `w:rPr` 格式信息。**凡是涉及"变更部分见某底色"，必须回到原始 `.docx` 抽格式。**
2. **颜色语义必须来自文档自己的文字，不能自己猜。** "绿底 = 本次变更"这个结论只能来自
   版本记录/修订记录表里的说明（例如「变更部分见绿底」），不能因为"绿色一般表示新增"就认定。
   文档没写清 → 问用户，不要推断后当成事实往下做。
3. **一个开发任务只对应一个需求。** 一份"多文档"里装着好几个系统的好几个需求，
   但本次只对用户选中的**那一条**负责。用 `ask_user_question` 让用户**单选**；
   确定之后不要再"顺手"把别的需求也做了——那不是帮忙，是把范围搞乱了。
4. **同一个文件里，不同片的底色可能不一样。** 必须逐片确认该片本次使用的标记色，
   不能把第一片的绿底约定套到第二片上。
5. **系统和模块靠目录级别区分，不靠猜。** 用标题的大纲级别（`w:outlineLvl`）或标题样式
   搭出层级骨架（见 A0），别靠字号、加粗、页眉去"感觉"层级——拼接文档里各片样式并不统一。
6. **只读上游。** 不改 `Pipeline/需求/source/`、`parsed/` 和 `requirement.json`——
   那是工作台的资产，改了会让原文、元数据和分析互相打架。
7. **没写的就是没写。** 推断必须显式标注「推断」。需求文档最贵的失败不是漏读，
   是把没写的当写过了。

> **如果没有人可以问（无人值守 / 只读模式）**：本 skill 里"问用户"的地方
> **仍然要走完** —— 把问题**逐条原样写出来**，再给出"默认假设下我会怎么继续"，
> 并**显式标注哪些结论建立在默认假设上**。
>
> 两条的优先级：**铁律 2（不猜）高于"必须问"**。无法问时允许带着标注继续，
> 但**绝不能把推断说成文档写了的**；确实定不下来的（例如一个没有任何依据的颜色），
> **就让它悬着**，不要硬填一个答案。
>
> 只读场景下 A8 的产物**用文本形式交回给调用方**，
> **不要为了"完成任务"去写盘**；同时说明"按纪律未落盘"。

---

## 2. 第一步：判定文档形态（决定走哪条路）

> **先把"多文档"这个词说准。** 用户说"多文档"，指的**不是**多个文件，而是
> **一个 Word 里装了好几个文档**：多系统、多功能点、**多处修订记录表**——
> 一份被拼装出来的文档。所以判定只看**这一个文件内部**长什么样，
> 跟用户上传了几个文件无关：哪怕只上传一个 `.docx`，也完全可能判定为 A 类。
>
> 记录表里**一行就是一条独立需求（各自一个 XQ 编号）**，所以一个 Word 里常常
> 装着好几条需求——这正是它被叫做"多文档"的原因。而**本次任务只做其中一条**。

拿到文档后**先做判定，再动手**。判定结果决定后面完全不同的两条路径。

| 判定信号 | 倾向 |
|---|---|
| **【最强信号】同一个文件内出现多处修订记录/版本记录表**（常见形态：每个系统一张、每章末一张） | **A 类** |
| 一个文件里覆盖**多个系统**（如 CRM + ERP + 工单），各自成章 | A 类 |
| 修订记录表里一行一条需求，带 `XQ…` 编号 + 需求名称 + 变更说明（+ 变更位置/底色约定） | A 类 |
| 目录里出现**多条并列的顶级条目、各自是一个系统**（一级标题 = 系统名），或章节编号在文件内重复/重置（出现两个"第 1 章"） | A 类 |
| 单一主题、章节编号连续、功能说明完整、无修订记录表 | B 类 |
| 只有一个人名/一次编制、无版本表、无底色标记 | B 类 |

**判定顺序——先数修订记录表的「处数」：**

1. **≥ 2 处表 → 直接 A 类。** 这就是"多文档"的典型标志，不要再犹豫。
2. **恰好 1 处表 →** 表里带"变更标记约定"（如"变更部分见绿底"）→ A 类；
   不带、但表里有 ≥ 2 行需求 → 仍 A 类，但**必须先问用户变更范围怎么界定**。
3. **0 处表 →** 再看是否多系统 / 有拼接痕迹。是 → A 类，但**必须先问用户变更范围**
   怎么界定（没有记录表就无从区分变更与原有内容，硬做必然靠猜）；否 → B 类。

- **A 类 → 走第 4 节（找齐记录表 → 需求清单选择 → 按标记色抽变更）**
- **B 类 → 走第 5 节（按功能模块三层分析）**

**两类都不像、或两类都像时：停下来问用户**，把判据摆出来让他定。
不要为了"往前走"硬选一条——A/B 的产物粒度不同，选错等于重做。

> **一个文件可以是多文档；多个文件也可以是同一条需求的分片。**
> 两种情况都按"先把所有修订记录表找齐，再合并成一份全局需求清单"来做（见 A1–A2）。

## 3. 抽出格式信息（技术规范，A 类必用，B 类也建议先做）

> **边界约定（当前阶段）**：底色识别由**本次读取时临时抽取**，不依赖工作台改动。
> 工作台的解析器目前只输出纯文本、不保留格式，这不是可以绕过的现状，而是本 skill
> 必须自己处理格式的原因。等 A 类路径在真实文档上验证稳定后，再考虑是否把格式
> 固化进解析器（那时 `parsed/*.txt` 才可能自带标记）——**在那之前，不要假设
> `parsed/*.txt` 里有任何底色信息**。

### 3.1 底色在 `.docx` 里的真实位置

`.docx` 是 ZIP，正文在 `word/document.xml`（样式在 `word/styles.xml`）。
底色**不是文本的一部分**，而是挂在三个不同层级的 XML 属性上：

| 层级 | XML 位置 | 语义 | 变更的最小单位 |
|---|---|---|---|
| 文字（run） | `w:r/w:rPr/w:shd/@w:fill` | 这一段字有底色 | 该 run 的文字 |
| **段落标记** | `w:p/w:pPr/w:rPr/w:shd/@w:fill` | **段落标记自身**的字符格式，**不是段落底纹** | 该段 |
| 段落 | `w:p/w:pPr/w:shd/@w:fill` | 整段有底色 | 整段 |
| 表格单元格 | `w:tc/w:tcPr/w:shd/@w:fill` | 整格有底色 | 整格 |
| 表格行 | `w:tr/w:trPr/w:shd/@w:fill` | **整行有底色** | 整行 |
| 整张表格 | `w:tbl/w:tblPr/w:shd/@w:fill` | 整表底色 | 整表 |

> **`w:pPr/w:rPr` 极易漏，而且漏了不容易发现。** 它是**段落标记自身**的字符格式，
> 与 `w:pPr/w:shd`（段落底纹）只差一层，含义完全不同。
> 漏掉它的后果是**统计对不上**——例如荧光笔实际 5 处、只数 run 级 `w:rPr` 会得到 3 处，
> 于是误判"这个标记只作用在文字上"，进而错判标记的粒度。
> **所以 run 级格式要同时看 `w:r/w:rPr` 和 `w:p/w:pPr/w:rPr` 两处。**

**表格的斑马纹**（隔行变色）常由 `w:tblLook`（`firstRow`/`band1Horz` 等）配合表格样式生成，
**它不是变更标记**，要按 3.3 回溯样式后排除。

另外两种"底色"表达方式，别漏：

- `w:rPr/w:highlight/@w:val` —— Word 的"荧光笔"，**是命名色**（`green`、`yellow`、`red`、
  `cyan`、`magenta`、`blue`、`darkGreen`、`lightGreen`、`darkYellow` 等），不是 hex。
  命名色表要单独映射，别当成 `w:shd`。
- `w:shd/@w:val` 取值：`clear`（纯色填充）、`solid`、`nil`（无）。
  `w:fill="auto"` 或 `w:val="nil"` 表示没有底色。

> **`w:pPr/w:rPr` 与 run 级不一致时怎么办**（例如段落标记带黄、run 带绿）：
> **以 run 级为准** —— run 级才是"这段文字本身带这个标记"；
> 段落标记常常只是 Word 跟随该段最后一个 run 自动写入的残留。
> 两者不一致时**把这处列出来问用户**，不要自己挑一个当准。

**先判断标记的粒度**：如果整格绿、整行绿，那"变更的最小单位"就是那一行/那一格，
不要在格子里再切字。粒度判断错了，功能点会碎成一堆单字。

### 3.2 别只看颜色：其它变更标记

按可信度排序，**优先级从高到低**：

1. **修订模式**（`w:ins` 插入 / `w:del` 删除，含 `w:insText`/`w:delText`）——
   这是 Word 自己记的变更，比底色权威。**两者都有时以修订标记为准**，并在回报里说明。
2. **底色 / 荧光笔**（见 3.1）——文档用颜色人工标注的变更范围。
3. **删除线**（`w:rPr/w:strike` 删除线、`w:rPr/w:dstrike` 双删除线）、
   **文字颜色**（`w:rPr/w:color/@w:val`）、加粗、下划线——辅助信号。
   删除线值得单独留意：它常用来标"这段要删掉"。但这些信号单独出现时**不足以**
   断定是变更，只能作为佐证，需要跟用户确认。
4. **批注**（`w:commentReference` + `word/comments.xml`）——常写着"这里为什么改"，是理解变更意图的金矿，值得单独读。

### 3.3 样式继承：底色的"隐形来源"

`w:shd` 可能不直接写在 run 上，而是来自：

- 段落样式：`w:pStyle` 指向 `styles.xml` 里的 `w:style`，其中 `w:pPr/w:shd` 生效；
- 字符样式：`w:rStyle` 同理（`w:rPr/w:shd`）；
- 表格样式 / 条件格式：`w:tblStyle` + `w:tblLook`（首行、首列、banding 等）。

**所以必须解析 `styles.xml` 并沿 `basedOn` 链回溯**，否则会把"表头样式"误判成"变更标记"。
实践中最常见的误报：`EFEFEF` 这类浅灰是**表头装饰**，不是变更标记。
（本工作区两份 CRM 文档里的 20 处 `w:shd` 全部是 `EFEFEF` 表头灰——典型的"有底色但无变更语义"。）

### 3.4 颜色归类：按色系，不按 hex

同一个「绿底」在不同人手里可能是 `C6EFCE`、`00B050`、`92D050`、`D9EAD3`——
**不要精确匹配 hex，要按色系归类**。把 hex 转 HSL 后判断：

| 色系 | Hue（度） | 备注 |
|---|---|---|
| 红 / 粉 | < 20 或 > 330 | |
| 橙 / 黄 | 20 – 70 | |
| 绿 | 70 – 170 | |
| 青 / 蓝 | 170 – 260 | |
| 紫 | 260 – 330 | |
| **灰 / 白** | 任意色相但**饱和度 < 12% 或亮度 > 92%** | **大概率是版式（表头、斑马纹），不是变更标记** |

`w:highlight` 的命名色直接按名字归类（`green`/`darkGreen`/`lightGreen` → 绿）。

### 3.5 提取脚本的约定输出

写一次性脚本抽取（`node` 可用；`.docx` 是 ZIP，`node:zlib` 的 `inflateRawSync` 直接解，
不必装依赖）。**输出必须是带标记的结构化文本**，而不是纯文本，例如：

```
[H1 3][outlineLvl=0] CRM 客户关系管理系统
[H2 12][outlineLvl=1] 2 总体要求
[P 14][pStyle=7 → shd=EFEFEF(样式继承)] 版本记录
[TBL 3]
[TROW 1][tcShd=nil] 需求编号 | 需求名称 | 变更说明
[TROW 2][tcShd=nil] XQ2026****-0001 | 客户信息优化展示 | 变更部分见绿底
[H2 45][outlineLvl=1] 3 客户主数据
[H3 46][outlineLvl=2] 3.1 客户信息展示
[P 47][run shd=C6EFCE(直接)] 列表增加「客户等级」列，并支持按客户等级筛选。
[P 47][run shd=C6EFCE(直接)+strike] 备
[P 48][shd=nil] 支持按客户名称模糊查询。
```

每个片段都要能回答五件事：**它的标题层级（A0 骨架靠这个）、它在哪（章号/段落序号）、
有没有底色、什么色、**来自哪（直接属性还是样式继承）**。
少任何一项，后面的"变更定位"和"骨架归属"就是瞎猜。

> **「来自哪」不是可选项，而且示例必须演出来。** 同一个 `EFEFEF`：
> 如果它来自**样式继承**（`pStyle=7` → `styles.xml` 里 Table Header 的 `w:pPr/w:shd`），
> 那是**版式**；如果是**直接挂在 run 上**，那才可能是人手工标的。
> 不标来源，就分不清这两者 —— 而这恰好是最常见的误判来源。
>
> 建议的标注写法：`(直接)` / `(样式继承)`，并带上样式 id 或名字。

> 例子里 `[P 47]` 的 **`P` 是段落序号**，**不是页码**。
> **`.docx` 里根本没有页码**——分页是 Word 渲染时才算出来的，`document.xml` 里
> 只在保存时留下 `w:lastRenderedPageBreak` 这类**提示**（可能过期、可能缺失）。
> 所以位置一律用 **段落序号 + 所属章节**表达，**不要承诺页码**。
>
> **段落序号的口径要写死**（否则每个人报的位置都对不上，报告就没法核对）：
>
> 1. **只数 `w:body` 的直属段落**，表格单元格里的 `w:p` **不计** ——
>    一份文档里表格内段落可以占一多半，算不算会让所有位置整体漂移；
> 2. **空段落也占一个序号**（不要跳过）—— 否则增删一个空行会让后面全部位移；
> 3. 表格位置用"**段 N 之后 · TBL M**"表达。

**标题必须单独标注层级**（`outlineLvl` 或解析出的标题样式名），不要混在普通段落里——
A0 要拿它搭骨架，A1/A5/A6 都要回来查它。表格也要带上行号，
因为记录表的"每一行"就是一条需求。

### 3.6 自检：先把"抽到了什么"给人看

抽完**先回报一张统计表**，再做分析：

- 各色系出现次数（绿 N 处、黄 M 处、灰 K 处……）
- 灰色 / 可疑装饰色的占比
- **每个颜色的来源分布**（直接属性 / 样式继承）
- 本次认定的"变更标记色"是什么、依据是哪一句话

> **"一处"怎么数，也要写清楚**：**一个 `w:shd` / `w:highlight` 属性算一处**
> —— 不是"一个 run 一处"，也不是"一个段落一处"。
> 报的时候**顺带写上"涉及几个段落"**，口径不同的人才能对上账。

> **⚠️ 先排除"是自己没抽到"，再去怀疑文档。这一步不能跳。**
>
> - **颜色统计为空、或只有零星几处** → 先回头验证**解析器是不是取错了层级**
>   （把 `w:rPr` 取成了 `w:pPr`、样式层过滤多剥了一层之类）。
>   **"文档真没有底色"和"脚本没读到"表现完全一样。**
> - **标题骨架为空** → 同理，先怀疑解析器，再去怀疑"文档没有大纲级别"。
>
> 这不是假想的风险：真实发生过 —— 抽取脚本取错一层，输出的"大纲级别汇总为空"
> 与"文档确实没写 outlineLvl" indistinguishable，于是骨架为空、后面全部结论作废。
> **稳妥做法：先用一个已知答案的小样本（例如只有一处底色的段落）验证脚本读得对，再跑全篇。**

**判断"规模相称"要有口径，不要凭感觉。** 拿两个数逐章对：

- **实际抽到的变更片段数** —— 选中那一行声明的各片里，带该标记的片段总数；
- **该行"变更位置"列声明的章节数**。

**每一章都至少抽到 1 处**就算相称，照常往下走。出现下面任一种，**先停下来问用户**：

- **有整章一处都没抽到**（声明了 3 章，只抽出 2 章的）；
- **总共只抽到 1–2 处，而声明的章节数明显更多**。

这两种都指向**漏抽了某一片**，补救动作是**回 A1 复查找表有没有漏**。
确实只有一两处变更、且逐章都覆盖到了，就不要无谓打断。

> **"灰色占比高"是另一回事，别和上面混为一谈。** 灰 / 白通常就是版式（表头、斑马纹），
> 占比高**本身很正常**，不构成停下来的理由。真正该停的是
> **"有个颜色在登记表里找不到依据"**（见 A4）——
> 那要**问用户这个颜色是什么意思**，**不是"回 A1 补表"**：
> 表可能一张都没漏，问题是这个颜色压根没有约定。
> 把两件事混在一起，会让人白跑一趟去找一张并不存在的表。

### 3.7 拿不到 OOXML 时（PDF / 老式 `.doc` / 扫描件）

1. 优先让用户提供 `.docx` 原件——A 类没有格式就无法可靠区分变更。
2. 退而用 PDF 的文本层 + 渲染：把相关页**渲染成图片**后用 `read_image` 直接看底色，
   靠视觉判断变更范围（这是"人在看"的等价物，可用但要说明依据是视觉判断）。
3. 只有纯文本时，**明确说清无法识别底色约定**，改走"与上一版逐行 diff"或请用户指明变更范围。

### 3.8 大文档：先建索引，再按需读正文

一份多系统文档动辄上百页，**不要一次性把全篇正文读进上下文**——既装不下，也会淹没重点。
分两层读：

**第一层：只抽索引（便宜，先做）**

- A0 的标题骨架（层级 + 位置区间）
- **所有表格**（A1 的记录表要靠它）
- 各色系的出现位置统计

> **"索引层"到底包含什么，这里写死**（否则每个人划的边界都不一样）：
>
> - **算索引层**：全部标题段落（含大纲级别）、全部表格（含表头与每格文字）、
>   全篇的颜色/标记统计（按段落序号定位）。
> - **不算索引层**：非标题、非表格的**正文段落内容**。
>
> 形态判定、A0 骨架、A1 找表**都依赖索引层**，所以这些必须先读，
> 这和"不要提前读正文"不冲突。**选完用户之后才读正文。**

拿到索引就足以完成：形态判定、A0 骨架、A1 找表、A2 合并清单、A3 让用户选。
**用户选完之前，不要读正文。**

**第二层：只读选中需求相关的正文**

- 按 A5 确定的片，**只抽那几片**的正文
- 每片都要带上**上下文**：所属功能块的无底色内容——A6 判新增/变更、A7 取现状都要它
- 别的片、别的系统的正文**不读**

这样一次任务的上下文量与"选中的那一条需求"成正比，**与文档总页数无关**。

## 4. 路径 A：一个文件里的多系统 / 多处修订记录

### A0. 先按目录级别搭出层级骨架

多系统文档靠**目录级别（大纲级别）**区分系统和模块——不靠页眉、不靠文件名、
也不靠读出来的"感觉"。所以第一件事是把标题层级抽出来，搭成骨架。

- **怎么取层级**：优先用段落的**大纲级别** `w:pPr/w:outlineLvl`（0 = 一级，1 = 二级……）；
  没有显式大纲级别时退回**标题样式**（`w:pStyle` 指向 `Heading1`/`标题 1` 之类，
  注意样式名可能是中文或带前缀，要沿 `styles.xml` 解析而不是字符串匹配）。
  **不要靠字号或加粗猜层级**——拼接文档里各片的样式经常不一致。
- **常见的层级约定**（先按这个假设，再用文档自己的目录页核对）：

  | 级别 | 通常是 | 例 |
  |---|---|---|
  | 一级 | **系统** | CRM 客户关系管理、工单系统 |
  | 二级 | **模块** | 客户主数据、商机与报价 |
  | 三级 | **功能块 / 功能点** | 客户列表、商机执行情况查询 |

- **产出骨架表**，后面 A1/A5/A6 全都要查它：

  | 系统（一级标题原文，去章号） | 模块（二级标题原文，去章号） | 功能块（三级） | 位置区间（段落序号） |
  |---|---|---|---|
  | CRM 客户关系管理系统 | 客户主数据 | 3.1 客户信息展示 | 段 210–330 |
  | 工单系统 | 工单受理 | 7.2 工单列表 | 段 520–600 |

  > 骨架里存**标题原文**（去掉开头的章节编号），`group` 就直接从这两列拼出来
  > —— 不要在这张表里就把它缩写成 `CRM`，那样后面拼 `group` 时就没法逐字取值了。

- **文档有目录页时以目录为准**：它比正文标题可靠，而且能立刻暴露"章节编号重复"这种拼接痕迹。
- **级别约定可能和上表不同**（有的文档一级就是模块，压根不分系统）。
  判断依据是顶级标题**是不是系统名**（CRM、ERP、工单系统这类产品/平台名）；
  对不上就按实际层级用，并在回报里说明你把哪一级当系统。
- **各片样式不统一时**（一片的 Heading1 是系统、另一片是模块），按目录页统一；
  统一不了就问用户，不要自己拍。

### A1. 找齐**所有**修订记录表（不是找到一张）

这是路径 A 最容易做错的一步：**只找到第一张表就开始干活**。
一个拼装文档里，修订记录表通常是**每个系统一张、或每章末一张**，
开头那张只覆盖它自己那个系统。漏掉后面的表，就等于整块需求都没看见。

做法：

1. **扫全篇所有表格**（`w:tbl`），不要只看文档开头。
2. 逐张判定"是不是记录表"：表头含 `版本/修订/变更/修改/日期/修订人/说明` 里
   任意两项以上，且 ≥ 2 列。**靠表头特征判定，不要靠表名**——
   很多拼接文档的表根本没有标题行。
3. **分清它是哪一类记录表——这一步不能省。** 两类表长得很像，但**其中一类的行根本不是需求**：

   | 类型 | 怎么认 | 一行是什么 | 用途 |
   |---|---|---|---|
   | **版本 / 修订历史表** | 表头是「版本 / 日期 / 修订人 / 说明」这类，**没有「需求编号」列**；通常在文档头 | 一次**改版**（v1.0 / v1.1 …） | **只用来提取颜色约定**，**绝不产出需求条目** |
   | **需求清单表** | 表头有「需求编号」列，或每行带 `XQ…` 之类的编号 | 一条**独立需求** | 既要颜色约定，**也是需求条目的唯一来源** |

   > **这是最容易出事的一处。** 版本历史表完全能通过第 2 步的关键词检验，
   > 但它的行（v1.0 / v1.1 / v1.2）**不是需求**。把它的行当需求提取，
   > 会凭空造出「1-2-v1.0」这种假需求，**直接污染给用户选的清单**，
   > 而用户很可能随手选一条，后面全白做。
   > **认不出是哪一类，就问用户** —— 不要靠"给它补个编号占位"蒙混过去。
4. 记下每张表的：**所在位置**（段落序号 + 上方最近的标题）、**类型**、
   **覆盖范围**（按 A0 骨架判断它落在哪个一级标题、即哪个系统下）、**行数**。

   > **行数一律双记「含表头 N（数据 M）」** —— 只写"3 行"，没人知道算没算表头，
   > 而两种口径差一行，核对时就会对不上账。
5. 先产出这张清单，再往下走：

   | # | 表格位置 | 类型 | 覆盖的系统/模块 | 行数 | 是否含底色约定 |
   |---|---|---|---|---|---|
   | 1 | 段 14 · 文档头 | 版本历史 | 全局 | 3 | 是（"变更部分见绿底"） |
   | 2 | 段 640 · 第 3 章末 | 需求清单 | CRM | 5 | 是（"见绿底"） |
   | 3 | 段 1180 · 第 7 章末 | 需求清单 | 工单系统 | 4 | 是（"补充见黄底"） |

**表数 ≥ 2 且这几张表没找齐之前，不要进入 A2。** 找齐了再合并。

其它要点：

- **表头可能不在第一行**（前面常有合并单元格的标题行），要往下探。
- **一个需求可能跨多行**（续行、子项），要按编号列归并。
- **变更标记的约定可能写在单元格文字里**（"变更部分见绿底"），也可能写在表下的说明段里，
  两种都要扫。措辞变体很多：见绿底、绿色底纹、标绿、以黄色标注、灰底为原有内容……
  **版本历史表和需求清单表里都有可能出现约定，两张都要扫。**
- **不同表的约定可以互相矛盾**（表 2 说绿底、表 3 说黄底）。矛盾时不要自己裁决，
  按 A5 逐片登记，并把矛盾点回报给用户。
- **全局约定与分需求约定并存时**（文档头写"本次变更部分见绿底"，而各系统表又各自声明），
  **以分需求那一行的约定为准** —— 全局那句定位不到具体需求，只能当背景。

### A2. 跨表合并成一份全局需求清单

**只从「需求清单表」提取条目。** 版本 / 修订历史表在 A1 已归为"只供颜色约定"，
它的行**一律不提取**（那不是需求）。把各张需求清单表的条目合并成一份：

```
编号：XQ2026****-0001（**只在需求清单表内**确实没有编号列时，才用"表序号-行号-名称"占位）
名称：客户信息优化展示
变更说明：原文照抄，不要改写
标记约定：绿底（来自哪张表、哪句话）
          **一条需求可能有多套约定** —— 逐片列出来，例如
          「绿底（CRM 片）+ 黄底（商城片）」，不要只留一个
所属系统：CRM（该表覆盖的系统）
涉及章节：3.1、附录B（表里写了就填，没写就空）
```

- **同一编号在多张表里出现 → 合并成一条**，但每张表说的都留下（说明可能互相补充，
  **标记约定尤其要合并**：同一需求在不同系统片用不同颜色是常态）。
- **同一名称、不同编号 → 分开列**：可能是两个系统里的同名需求，不要合并。
- **变更说明照抄原文。** 这是用户用来做选择的依据，改写会让两个选项看起来一样。

### A3. 列出清单，让用户**单选**（硬门槛）

**一个开发任务只做一个需求**，所以这里是**单选**，不是多选。

用 `ask_user_question` 把候选摆给用户：

- 选项标签：`[编号] 名称`
- 选项说明：变更说明原文的前半句（+ 所属系统，帮他区分同名需求）
- 候选按 A0 骨架的系统分组排序，同一系统的排在一起
- 候选很多（> 10）时，先让用户选**系统/模块**缩小范围，再选具体需求

> **两种文档形态都常见，两条路都要走通：**
>
> - **一个 Word 只装一条需求**（清单只有 1 条）→ 仍然**确认一次**
>   （"只识别到 1 条，就按它做？"），不要默默往下走。这种形态下
>   文档里那条 XQ **应当就是**当前需求文件夹的编号，核对尤其要紧
>   （对不上多半是传错了文件）。
> - **一个 Word 装多条需求**（清单 > 1 条）→ 让用户**单选**一条。
>
> 两种形态的核对动作完全一样，见下面的防错档。

**用户没选之前，不要开始抽变更内容。** 这是整条路径的闸门。

**选完立刻核对编号（防错档）**：把选中的 XQ 编号与**当前需求的编号**
（`requirement.json` 的 `id`，或需求文件夹名）对一遍。

- 一致 → 继续。
- **不一致 → 停下来问用户**，不要往下做。一份 Word 里装着 20 条需求，
  选错一条的后果是**给 B 需求的功能点被记到 A 需求名下**，
  而且因为功能点带 `source`，事后很难看出来。这是最贵的一类错误。
- **根本没有比对对象**（用户只是丢来一份文档、没走工作台，工作区里没有对应需求文件夹）
  → 这**不是"不一致"**，按"读文档、不挂工作台"继续：跳过 A7 第 7 步的已有功能点比对，
  全部按新增处理，并在回报里**明说"没有编号可核对、也没有可比对的已有功能点"**。
  **不要因为找不到比对对象就把整条路径停下，也不要假装核对过了。**
- 用户坚持要做不一样的编号 → 让他确认目标需求文件夹，别自己改路径。

选中之后，**本次任务的范围就只有这一条**：其它需求的变更内容即使带同样的底色，
也不要顺手分析、不要写进功能点清单。范围外的内容最多在回报里提一句。

### A4. 建立标记语义登记表（按「标记方式 × 颜色」逐行登记）

把 A1 各张表里关于标记的约定**汇总成一张登记表**，这是后面所有判断的依据。

> **必须按「标记方式 × 颜色」分行，不能只按颜色分行。** 理由有两层，
> 真实文档各踩中一层：
>
> - **同色不同机制**：`w:shd` 的黄**底** 与 `w:highlight` 的黄色**荧光笔**是两套东西，
>   在一份文档里可能分属**两条不同的需求**。按颜色合并成一行，这两条就再也分不开了。
> - **同色系不同语义**：浅绿 `C6EFCE`（标"变更部分"）与鲜绿 `92D050`（标"整块新增"）
>   同属绿色系，却承担**不同语义**。3.4 说"按色系归类"是为了防"把同义的拆开"，
>   **不是**要你把不同义的合并 —— **语义由记录表的文字决定，不由颜色决定**。

| 标记方式 | 值 | 语义 | 依据（哪张表、哪句话） | 适用范围 |
|---|---|---|---|---|
| 底纹 `w:shd` | 绿 `C6EFCE` | 本次新增/修改的内容 | 表 2："变更部分见绿底" | CRM 2.1.1 / 2.1.3 |
| 底纹 `w:shd` | 鲜绿 `92D050` | 整块新增功能的内容 | 表 2："新增功能，绿底为新增内容" | CRM 2.1.2 |
| 底纹 `w:shd` | 黄 `FFF2CC` | 商城侧配套变更 | 表 3："商城侧配套变更见黄底" | 商城 2.3.1 |
| 荧光笔 `w:highlight` | `yellow` | 另一条需求的变更 | 表 1："变更部分以荧光笔标注" | 附录 |
| 底纹 `w:shd` | 灰 `EFEFEF` | 表头装饰（**非变更标记**） | 样式继承自 Table Header，全篇 16 处 | 全篇 |
| 无底色 | —— | 原有内容（**仅对"变更功能"成立**，见下） | —— | 全篇 |

要点：

- **每一格都要填**（标记方式 / 值 / 语义 / 依据 / 适用范围）。填不出来时**分两档**处理，
  不要留空继续，也**不要一律去问**：
  - **灰 / 低饱和度**（按 3.4 判为版式的）→ **直接判为版式并排除，不必问用户**。
    灰底太常见了（表头、行强调、隔行色），逐个问会把流程拖死。
  - **其它颜色找不到依据** → **停下来问用户**。这类才可能是真正的变更标记：
    默默排除会漏活，自己认定则是瞎猜。
- **语义一律以记录表的文字为准**，不要从颜色本身推断 ——
  "绿色通常表示新增"这种想法是明令禁止的（见铁律 2）。
- **同一个 hex 可以服务多条需求**（靠"变更位置"列切片，见 A5）；
  **同一个语义也可以对应多个 hex**（记录表都写"绿底"，实际一个 `C6EFCE`、一个 `92D050`）。
  这种"一个词指代多个 hex"的情况，**不要按色系合并**：
  先用**变更位置列**切开范围，再看**该片内实际只出现哪一种 hex** ——
  靠这两步锁定本次是哪个；锁定不了就问用户。
- **一段文字上叠加多种标记时，先看是不是同一种颜色**：
  - **同色叠加**（例如黄底 + 黄色荧光笔）→ **算一个标记**，
    只是同一次标注的两种表现形式；按其中任一种登记即可。
  - **异色叠加**（例如黄底 + 青色荧光笔）→ **算两个独立标记**，
    **各自都要在登记表里查得到依据**；有一个查不到，就按上面那两档处理
    （灰系排除、其余问用户）。不能因为"另一种标记已经能定位了"就把它忽略掉。

> **例外**："无底色 = 原有内容"**只对已确认是"变更功能"的功能块成立**。
> 整块新增的功能可能完全没有底色（见 A6），这时无底色不代表"原有"。
> 所以顺序是：**先用 A6 分清新增还是变更，再回头解读底色**。

### A5. 逐片确定标记色（同一个文件内也要分片）

**这是"多文档"最容易翻车的地方**：用户选中的那一条需求，它的变更可能散落在文件的
好几个片里（第 3 章正文、附录 B 补充说明、第 7 章交叉引用的一段），而**每片本次用的
标记色可能不一样**——因为每片来自不同的人、不同的系统文档。

片按 A0 骨架的**目录位置**划分（在哪个一级标题下、哪一节、哪个附录），**不要按页分片**
——`.docx` 里压根没有可靠的页码（见 3.5），目录位置才是稳的。按片建立映射，逐片套用：

| 片（按 A0 骨架的目录位置） | 所属系统 | 本次标记色 | 依据 |
|---|---|---|---|
| 第 3.1 节正文 | CRM | 绿底 | 表 2 第 2 行"见绿底" |
| 附录 B 补充说明 | CRM | 黄底 | 表 2 第 5 行"补充部分见黄底" |
| 第 7.2 节 | 工单系统 | 绿底 | 表 3 第 1 行"见绿底" |
| 文档头版本表 | 全局 | 灰底 `EFEFEF` | 版式，非标记 |

规则：

1. **逐片套用该片自己的颜色**抽变更内容，不要跨片复用。
2. 片与片之间，**用户选中的同一条需求要合并成一份功能点清单**，
   不要一个片出一份互不相干的清单。
3. 某片在表里查不到约定时：**先统计该片实际出现了哪些颜色，再带着统计去问用户**，
   不要自己定。（"这片只有绿色出现且集中在变更段落"是合理假设，但仍要用户点头。）
4. 文件里出现**无法解释的第三种颜色**时（既不在登记表里，也不像版式），
   停下来问——**很可能漏了一张修订记录表，回 A1 补**。
5. **颜色是"哪条需求"的定位手段，不是全局的。** 记录表里每一行（每个 XQ）各自写着
   自己的标记色，所以**只抽选中那一条需求的行所声明的颜色**，别的 XQ 的底色一律不抽。
6. **颜色不足以区分需求时，用「变更位置」列切片。** 下面三种形态都会让颜色定位失效，
   真实文档里三种都出现过：

   | 形态 | 长什么样 | 怎么切 |
   |---|---|---|
   | **同一片、两条需求、同一个颜色** | 两行都写"见绿底"，都指向 3.2 | 用各自的**变更位置**列切范围 |
   | **不同片、却是同一个颜色** | 选中 XQ-0001，但那个绿 `C6EFCE` 同时也出现在 XQ-0003 / XQ-0004 的章节里 | 用**变更位置**列只保留本次那几片；**并明确列出被排除的同色片段** |
   | **两条需求的变更位置列完全相同** | 两行都写"1.1.1" | 位置也切不开时，看**标记方式**（A4 那六列）是否有别（例如绿底 vs 荧光笔）；**仍然切不开就问用户** |

   **千万不要把别的 XQ 的变更混进来。** 范围外的同色片段要在回报里点名，
   让人能核对你既没漏、也没多。

### A6. 先分清「新增功能」还是「变更功能」（核心判据）

抽到带底色的内容后，**第一件事不是比对，而是判断这个功能块属于哪种形态**——
两种形态的产物完全不同，判错了后面全错。

| 形态 | 判据 | 含义 | 产物 |
|---|---|---|---|
| **新增功能** | 该功能块（三级标题下的**全部**内容）整体都是同一个底色，且与记录表里那一行的描述对得上 | 这是一个**全新的功能块**，文档里不存在它的"原功能" | **新功能点**：直接展开成要开发的内容，**不需要**与原功能比对 |
| **变更功能** | 功能块下**只有部分内容带底色**，其余**无底色** | 无底色 = **原功能描述**（= 工程中已实现的功能）；有底色 = **本次要改的内容** | **改造功能点**：按「原 → 新」写 |

**怎么判**：看三级标题往下的全部片段——

- 几乎整块都带同一底色 → **新增功能**
- 底色只覆盖其中一部分（哪怕只有一句话、一个字段名）→ **变更功能**
- 混杂、拿不准 → **问用户**，不要猜

**两个容易漏判的场景：**

- **整块新增可能发生在更高的层级**：一整个**模块**甚至**系统**都是新的时候，
  同样按"整块是不是同色"来判，不要只在三级标题上找。
- **整块新增可能完全没有底色**——新章节直接写进去、压根没标色。
  这是**最容易漏的一类：只搜颜色会得出"无变更"的错误结论**。
  判断靠两条证据，**任一成立即可**（不要求同时成立 —— 很多场景下根本没有"上一版"可比）：

  1. **记录表那一行的描述**写了"新增模块 / 整章插入 / 未标注底色"这类话；
  2. **该章节在上一版里不存在**（工作台里确实有上一版文档时才用得上）。

  两条都查不到 → **问用户**，不要因为"没搜到底色"就当成没有变更。
  **只有记录表描述、没有上一版可对时，按第 1 条判定，并注明"仅凭记录表描述"。**

**如果文档同时开了修订模式**（`w:ins` / `w:del`，见 3.2）：**以修订标记为准**——
它本身就是"增 / 改 / 删"的权威记录，不用再靠底色去猜是新增还是变更。
底色只在文档**没有**修订标记时才当主判据。

**两条关键语义（请记牢）：**

1. **无底色 = 已经在工程中实现的功能。** 这就是"现状"的唯一来源，
   不需要额外的资料或代码库。
2. **有底色的内容本身通常写着要做什么。** "增加查询条件""优化页面展示""删除某个字段展示"——
   这些是**带底色文字里明写的动作**，不是文档里真有被删掉的旧文本。
   **要读出文字在说「增 / 改 / 删」，按语义分类**，不要去找并不存在的"被删除的原文"。
3. **但底色文字里可能一个动作词都没有** —— 真实文档常常只给一段带底色的字段名或句子，
   方向得从别处读：

   - **底色 + 删除线 = 删除类。** 这不是 3.2 说的"删除线单独出现"（那种不足以断定），
     而是删除线与**已声明的变更色同时存在** —— 此时它就是删除方向的**权威依据**，
     判为"移除 XXX"并**照样出功能点**，不必再回头问用户
     （但应在 `note` 里注明方向来自删除线，方便人复核）。
   - **删除线可能只覆盖词的一部分**（例如整词「备注」只有「备」字带删除线，
     是 Word 选区残留的常见结果）。**按语义单位理解** —— 读成"备注"整个词被删，
     **不要**判成"只删一个字"，也不要因为"不是一个完整的词"就当成误操作忽略掉。
   - 既没有动作词、也没有删除线时，才按 A6 的分流去归到增/改，**并明确标注「推断」**。

### A7. 从变更内容到功能点

对用户选中的**那一条**需求，按这个顺序做：

1. **定位变更内容**：按该片的标记色，抽出所有带该底色的片段（run/段/行/格，粒度按 3.1 判定）。
2. **定位所属功能块**：拿变更片段的目录位置去查 A0 骨架，取到它的
   **系统（一级）/ 模块（二级）/ 功能块（三级）**。
   `group` 按 **6.2 的规则**取 —— **先沿用工作台已有的 `group` 字符串，
   没有可沿用的才按骨架自己拼**。骨架里取不到就问用户，不要自己编一个层级。
3. **按 A6 分流**：
   - **新增功能** → 没有现状，直接进第 5 步；
   - **变更功能** → 取出该功能块内**无底色**的内容作为现状（原功能）。
4. **比对差异**（仅变更功能），归入四类。**判据只有一条：原功能里有没有这个东西。**
   不要凭"这句话读起来像优化"来归：

   | 类 | 判据 | 写法 |
   |---|---|---|
   | **增加** | **原功能（无底色部分）里完全没有**这个能力、规则或字段 | 直接写要做什么 |
   | **修改 / 优化** | **原功能里有，但口径 / 字段 / 规则 / 展示变了** | 写「原 → 新」 |
   | **删除** | 底色说要删的（含"底色 + 删除线"，见 A6） | 写「移除 XXX」—— **照样出功能点** |
   | **未变** | 无底色、且没被任何底色内容指到 | 一句话带过，不要罗列 |

   > **两个例子分清楚**（很容易归反）：
   >
   > - 原文只说"展示客户名称"，底色加了"超过 20 字以省略号展示" ——
   >   原功能里**没有**这条规则 → 归**增加**，**不是**"修改展示口径"。
   > - 原文已经在展示"客户等级"，底色改成"以彩色标签展示" ——
   >   原功能里**有**这个字段，只是展示方式变了 → 归**修改**。
5. **生成功能点**：每条增加/修改/删除出一个功能点，粒度见第 6 节。
   **新增功能**（整块同色那种）没有"增/改/删"条目可比，改按功能块内部的
   **能力 / 子结构拆点**——例如一整个新查询页，拆成"查询条件与列表""导出"
   "权限过滤"这样的几条，而不是整块一条、也不是每个字段一条。
   拆不准就按能力拆，并注明这几条同属一个功能块、可以合并派活。

   > **一条需求的变更跨多个系统时，功能点会分属多个 `group` —— 这是允许的**，
   > 但**必须在报告的显要位置写明"本次需求跨了 N 个系统：X、Y"**。
   > 不写的话，看报告的人会以为只动了一个系统，**派活时漏掉另一半**。
6. **对照校验（必做）**：拿记录表里这一行的描述，回头核对正文实际抽到的标记。

   **先判"是不是同一件事"——这是记录表与正文打架时的裁决规则。
   用三档，不要估百分比**（百分比会给出假精度，实际判断总落在临界线上，等于没判）：

   | 档 | 判据 | 怎么办 |
   |---|---|---|
   | **同一件事** | **要动的东西是同一个**：同一功能块、同一字段 / 页面、动作方向一致（增强 vs 增强） | **以正文为准**往下做，记录表描述只当索引 |
   | **部分相关** | 大方向对得上，但有一块对不上（表说"展示"而正文还含"导出"；或表声明的章节里只有一部分有标记） | **停下来问用户**，把两边摆出来 |
   | **明显无关** | 指向不同功能块 / 不同系统 / 动作方向相反 | **停下来问用户** |

   **判据是"要动的东西是不是同一个"，不是字面重合率。** 例子：

   - 表里"客户信息优化展示"、正文"客户列表增加标签筛选" → 同一功能块、同为增强
     → **同一件事**（正文只是更具体的说法）。
   - 表里"客户信息优化展示"、正文"新增商机导出" → 不同功能块 → **明显无关**。
   - 表里名称只说"展示"、而"变更位置"列含"导出" → **部分相关** → 问用户。

   **后两档一律问，不要自己裁决** —— 这是需求来源之间的冲突，不是你能定的。

   其余要核对的：

   - 表里说涉及 3 个章节，正文只找到 1 个 → **列出来**，很可能漏了标记
   - 正文里还混着**其它 XQ 的底色内容** → 剔除掉（本次只做这一条需求）
   - 表里说"见绿底"，绿底却落在别的功能块 → 列出来
7. **对齐已有功能点：能对上就"更新"它，不要新增**（硬规则）：

   - **先读** `requirement.json` 的 `featurePoints`（**只读，不要写**）。
     **没有这个文件时**（用户只是丢来一份文档、没走工作台）**跳过这一步**，
     全部按新增处理，并在回报里说明"没有可比对的已有功能点"。
   - **比对只在本需求范围内做。** 工作台里**别的需求**也有 `featurePoints`，
     但那些**不算比对对象** —— 拿它们来比会把 A 需求的功能点当成 B 需求的已有功能点。
     **跨需求比对需要用户明确授权**；默认不跨，并在回报里说明"未跨需求比对"。
   - 匹配用**去掉空白、忽略大小写**的名字——工作台就是这么比的，
     「客户信息 导出」和「客户信息导出」算同一条。
   - **对上了 → 这条变更是"更新"**：在 `points.json` 里加
     `"updates": "<已有功能点原文名>"`，`name` 与已有功能点保持一致，
     `note` 写本次改成什么样（「原 → 新」）。
     **不要再起一个新名字**——那会在工作台里造出一条重复的功能点。
   - **对不上 → 才是新增功能点**，按常规写。
   - 两种都要在 `analysis/vN.md` 里分成两份清单列出：**更新的**（原名 → 改成什么）、
     **新增的**。原因见 6.3 的警告：工作台当前还不认 `updates`，
     更新内容现在只能靠这份清单让人手工落。
   - 仍然**不要自己去改 `requirement.json`**。

### A8. 路径 A 的产物

- 变更识别报告：**修订记录表清单（几处、各覆盖哪个系统）** + 颜色语义登记表 +
  逐片标记色映射 + 该功能块是**新增还是变更**的判断 + 四类差异明细（带章节号）+
  对照校验结果（含正文与记录表的**契合度**判定）
- **更新的功能点清单（原名 → 改成什么）与新增的功能点清单**——
  当前把"更新"落到实处的**唯一途径**，必须写全写准（见 6.3 的缺口说明）
- `analysis/vN.md`（给人读，结构见第 7 节）
- `analysis/vN.points.json`（给工作台读）

## 5. 路径 B：单一主题、功能说明完整、无修订记录表

这种文档没有"变更标记"可依，价值在于**补出文档没写到施工层的那一层**。

### B1. 先搭章节骨架，再切功能模块

路径 B 也要搭骨架——`group` 要从这里取，不能凭感觉写。做法比 A0 简单：

- 用**大纲级别 / 标题样式**把标题层级抽出来（取法同 A0），列成：

  | 模块 | 功能块 | 位置区间（段落序号） |
  |---|---|---|
  | 客户主数据 | 客户列表 | 段 210–330 |

- **哪一级当模块按文档实际层级定**：多数文档是"一级 = 模块、二级 = 功能块"。
  单系统文档不必有"系统"这一层（见 6.2）。
- 用文档自己的章节名（如「客户主数据」「商机与报价」），**不要自造模块名**，
  也不要用"第一部分"这种位置词。
- 一个模块下如果跨了很多页，先看它有没有天然的子结构（查询页、列表页、详情页）。
- `group` 用**一模一样的字符串**重复，这是工作台把功能点显示成树的依据。

### B2. 每个功能模块做三层分析

对模块里的每个功能点，**必须把三个层面都过一遍**，缺一层就是漏活：

**① 前端页面开发**
- 页面/组件构成、入口在哪、和已有页面的关系
- 字段与控件：列定义、筛选项、表单字段、默认值
- 交互：查询/重置/分页/排序/导出/批量操作、二次确认
- 状态：加载中、空数据、出错、无权限、超长文本
- 校验与提示：必填、格式、范围、错误文案
- 权限可见性：哪些字段/按钮对本角色隐藏或置灰

**② 后端接口开发**
- 接口清单：方法 + 路径 + 用途（一个功能点常常是 1 个查询接口 + 若干操作接口）
- 入参/出参：字段名、类型、是否必填、分页与排序参数
- 校验与业务规则：参数校验、越权校验、状态校验
- 权限与数据范围：能查谁的数据（本人/团队/全部）
- 事务、幂等、并发：写操作能不能重复提交
- 错误码与提示；日志与审计

**③ 数据流向**
- 数据从哪来：哪些表/实体、上游系统、是否实时
- 怎么算：join 关系、聚合口径、金额/数量口径、时间口径（自然日 vs 工作日）
- 到哪去：展示、导出、缓存、下发
- 同步/异步、刷新时机、缓存失效
- 一致性：与上游对不上时以谁为准

**示例**——「客户商机执行情况查询页面」（用户给的例子，照此展开）：

| 层面 | 分析出的修改点 |
|---|---|
| 前端页面开发 | 查询条件区（客户、时间范围、阶段、负责人）；列表列定义（商机名称、客户、金额、阶段、赢率、预计成交日期、负责人）；分页与排序；导出；空态与加载态；金额千分位与单位 |
| 后端接口开发 | `商机执行情况查询` 接口（筛选 + 分页 + 排序）；权限过滤（按数据范围）；汇总行（金额合计、加权金额）；导出接口（大数据量走异步）；参数校验与错误码 |
| 数据流向 | 商机表 + 客户表 + 阶段表 join 口径；"执行情况"的金额口径（合同额/回款额/未回款）；阶段停留天数计算口径（自然日/工作日）；数据实时还是 T+1；与报表口径是否一致 |

### B3. 生成功能点：**每层各一条**

**前端页面开发 / 后端接口开发 / 数据流向各成一条功能点，不要合并。**

理由：这三层通常**不是同一个人做**（前端、后端、数据口径往往分开派活），
合并成一条会让这条功能点落不到任何一个具体的人手上。

- **同一个层面内部的多个小点要合并**：例如前端那一层的"查询条件 + 列表列 + 分页 +
  导出"合成一条「客户商机执行情况查询页面」，否则会碎成字段级、没法派活。
- `note` 里写清这一层具体要做什么。
- 三层用**同一个 `group`**，这样在工作台里会挂在同一棵树下。
- **逐条标「（推断）」**：B 类的结论大多没有文档原文支撑，所以每条都要回头问一句
  "**这句在文档里能找到原文吗？**"——找不到就在 `note` 里标「（推断）」，
  只有确实是文档原话的例外（例如文档明写"支持导出 Excel"）。
  **不要因为"整批都是推断"就一条都不标**——那正是这个标注要防的事：
  开发分不清"甲方要的"和"AI 猜的"。

以上面的示例为例，这**一个**功能块产出 **3 条**功能点：

| group | name | 层面 |
|---|---|---|
| CRM 客户关系管理系统 / 商机与报价 | 客户商机执行情况查询页面（前端） | 前端页面开发 |
| CRM 客户关系管理系统 / 商机与报价 | 客户商机执行情况查询接口（后端） | 后端接口开发 |
| CRM 客户关系管理系统 / 商机与报价 | 商机执行情况数据口径与取数（数据流） | 数据流向 |

（`group` 见 6.2：**先沿用工作台已有的**，没有可沿用的才自己拼。
上表是"没有可沿用 + 多系统"时的写法。）

### B4. 对齐已有功能点（与 A 类同规则）

B 类**也要做**这一步——需求文件夹里可能已经有上一轮分析填进去的功能点，
不比对就会造出重复点。

- 先读 `requirement.json` 的 `featurePoints`（**只读**）。**没有这个文件就跳过**，
  全部按新增处理，并在回报里说明。
- 按**去掉空白、忽略大小写**的名字比对（工作台就是这么比的）。
- **对上了 → 更新**：`points.json` 里加 `"updates": "<已有功能点原文名>"`，
  `name` 与已有保持一致，`note` 写本次要改成什么样。**不要另起新名字**。
- **对不上 → 新增**。
- 同样在 `analysis/vN.md` 里分列「更新的」和「新增的」两份清单
  （工作台当前不认 `updates`，原因见 6.3）。

### B5. 路径 B 的产物

- 每模块的三层分析表（上面那种表），**先给用户看**，再落功能点
- **更新的 / 新增的**两份功能点清单
- `analysis/vN.md` + `analysis/vN.points.json`

## 6. 功能点怎么写

### 6.1 粒度

**一个功能点 = 一件可独立交付、能被勾完成的事。**

- ✅ 「客户列表按标签组合筛选」
- ❌ 「客户模块」（太大，验收不了）
- ❌ 「支持 XX 能力」（没法验收，没说清做什么）
- ❌ 「修改前端页面」（不是一件事，是一类事）

### 6.2 命名与说明

- `name`：动词 + 对象 + 关键限定，20 字以内，**读的人能直接判断做没做完**
- `note`：一句话说清范围和口径；推断出来的内容在这里标注「（推断）」
- `group`：**先用工作台已有的，没有才自己拼。顺序不能反** ——
  这条规则存在的唯一理由是"让功能点在树里聚到一起"，
  而**自己造一个字符串，恰恰就是把它拆开的办法**。

  1. **先读 `requirement.json` 的 `featurePoints`。** 本次变更落到的那个模块，
     如果那里**已经有功能点**，就**逐字沿用它们的 `group`**（照抄，一个字都别改）。
     这是唯一能保证新点与旧点进同一棵树的办法。
  2. **沿用时可能看起来"不完整"，也要照抄。** 工作台既有数据里的 `group`
     常常**只有模块名**（如 `客户主数据`），**没有系统前缀**。
     不要"顺手补全"成 `CRM 客户关系管理系统 / 客户主数据` —— 那就又拆开了。
  3. **没有可沿用时**（新模块，或该需求还没有任何功能点）才自己拼：
     - **文档只有一个系统** → 只用**模块名**（二级标题去章号），如 `客户主数据`。
       这也与工作台既有数据的习惯一致。
     - **文档有多个系统** → 用 `系统名 / 模块名`（都逐字取自标题、去章号），
       如 `CRM 客户关系管理系统 / 客户主数据` —— 防止两个系统里的同名模块被拼到一起。
  4. 同一模块的 `group` 字符串**逐字相同**。自己拼时**不要缩写成骨架里不存在的短名**
     —— 骨架里是「CRM 客户关系管理系统」，就没有「CRM」这个字符串。
- **功能点要写清是"新增"还是"改造"**：新增功能的点直接写要做什么；
  改造功能的点写成「原 → 新」，这样派活的人一眼知道要动哪里。
  删除类的点写成「移除 XXX」。来源（哪一处底色 / 哪一章）放 `note` 里。

### 6.3 `points.json` 格式（与工作台对齐）

```json
{
  "schema": 1,
  "version": "v1.1",
  "points": [
    { "group": "CRM 客户关系管理系统 / 客户主数据", "name": "客户列表按标签组合筛选", "note": "多标签组合条件筛选（来源：绿底变更，3.1）" },
    { "group": "CRM 客户关系管理系统 / 客户主数据", "name": "客户列表导出", "note": "导出改为异步，超 1 万行走任务中心（原 → 新）", "updates": "客户列表导出" }
  ],
  "updatedAt": "2026-09-18T00:00:00Z"
}
```

- `updates`：**可选**，只在"这条变更对应工作台里**已有**的功能点"时出现，
  值是那条已有功能点的**原文名**。没有对应关系就不写这个字段。
- UTF-8、LF 换行，必须是能被 `JSON.parse` 解析的合法 JSON。

> **⚠️ 当前工作台还不认 `updates`——这是已知缺口，不要假装它能用。**
>
> `mergeExtractedPoints`（`dsh-client-ui-workbench/lib/client.js`）现在**只按名字比对**：
> 名字已存在就**整条跳过、一个字都不改**（只在没有分块时补一个分块名），
> 名字不存在才追加。于是：
>
> - 写了 `updates`、且名字与已有的一致 → **静默无效**，改动说明直接丢掉
> - 为了"让它生效"而换个新名字 → 工作台会**多出一条重复功能点**
>
> **当前阶段的决定：先只把「更新的功能点」清单列在 `analysis/vN.md` 里，
> 由人照着手工更新；插件支持 `updates` 留到后续再做。**
>
> 所以：
>
> - `points.json` 里**照常写 `name`（与已有功能点一致）和 `updates`**，
>   它是**预留字段**，不指望现在生效，但也不能省——省了将来就要回头改数据。
> - **真正交付的是 `analysis/vN.md` 里那份更新清单**，它必须写全、写准，
>   否则这次变更是真的没人落。
> - 后续做插件支持时，`mergeExtractedPoints` 应：按 `updates` 找到已有功能点，
>   更新它的 `note`，**保留 `id`、`assignee` 和已有的分块**（人已经派过活了）。

## 7. 产物落在哪

**如果本次是工作台「需求」模块派发的**，产物路径写死为：

- `docs/requirements/<需求编号>/Pipeline/需求/analysis/<版本>.md`（给人读）
- `docs/requirements/<需求编号>/Pipeline/需求/analysis/<版本>.points.json`（给工作台读）

`<版本>.md` 的结构与工作台既有约定一致（工作台按标题认它）：

1. 一句话结论
2. 关键信息：涉及的系统/模块、角色、数据实体、外部依赖
3. 需求要点：编号列出功能点（与 points.json **一一对应、顺序一致**）
4. 影响面与风险
5. 待澄清问题（一条一行，写成能直接拿去问产品的句子）
6. 与已有工作台数据的关系：**更新的功能点**（原名 → 改成什么）与**新增的功能点**分成两份清单。
   这份更新清单是**必交内容**，不是附注——工作台当前不会自动应用 `updates`，
   漏了它就等于这次变更没人落（见 6.3）。
   另指出哪些功能点在文档里找不到出处、哪些文档要求还没有功能点
7. **与上一版（vX.Y）的差异**（有上一版时才写，标题逐字写成 `## 与上一版（vX.Y）的差异`）
   - 路径 A 时，这一节直接引用 A7 的四类差异结论

**如果用户只是让你读文档**（没走工作台），默认写到 `docs/requirements/需求阅读-<日期>.md`，
或按用户当场指定的位置。**不要擅自去写 `requirement.json`**——功能点由工作台自己读
`points.json` 去填。

> **没有需求文件夹时，`points.json` 一个都不要写。** 它没有默认落点，
> 也没有工作台会去读它 —— 写了只会变成一个没人消费的孤儿文件。
> 这种情况把**功能点清单直接写进 `.md` 的第 3 节**交给调用方就够了。

> **只写本次选中那一条需求的功能点。** 一份 Word 里可能装着好几条 XQ 需求，
> 但一个需求文件夹只对应**一条**（文件夹名就是 XQ 编号）。
> 所以 `points.json` 里**只放这一条需求的功能点**，
> 不要把同一份文档里其它 XQ 的变更也算进来。

## 8. 收尾必须回报什么

1. **判定结果**：A 类还是 B 类，依据是什么（列判据，不要只说结论）
2. **骨架**：A0 / B1 搭出来的层级是否成立；覆盖了哪几个系统、各几个模块
3. **路径 A**：**共找到几处记录表、各是哪一类**（版本历史 / 需求清单）、各覆盖哪个系统、
   识别到几条需求、**用户单选了哪一条（XQ 编号）**、每片的标记色及其依据、
   **该功能块是新增还是变更**、四类差异条数
4. **对照校验结果**：正文与记录表那一行的**契合度**估了多少、是走了"以正文为准"
   还是"停下来问用户"；涉及章节/颜色对不上的逐条列出
5. **路径 B**：切了几个模块，每模块三层**各自**出了哪些点（三层 = 三条功能点）
6. **功能点数变化**：**更新了几条**（逐条写原名 → 改成什么）、**新增了几条**、
   总数从多少到多少。
   **本次需求跨了多个系统时，在这里显要标明"跨 N 个系统：X、Y"** ——
   否则看报告的人会以为只动了一个系统（见 A7 第 5 步）。
7. **待澄清问题**：颜色语义不确定、表里没写全、骨架层级对不上、新增/变更判不准的地方
8. **一句话结论**，**不要复述全文**
