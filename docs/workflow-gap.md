## 0. 目标流程（按你的描述整理）

```
需求老师下发文档
      ↓
① 上载需求文档 → ② 分析功能点（开发可调整）
      ↓
③ 方案分析（可调整）→ ④ 生成方案文档【模板】→ 上传流程系统
      ↓
⑤ 正式代码开发 → ⑥ 简单自测 → 测试报告【模板】
      ↓
⑦ 提版文档【模板】→ 提上系统 → 需求完成
```

一句话概括与现实的分水岭：**工作台现在产出的是"给人看的中间件"，现实流程要的是"能交给流程系统的正式文档"。**

## 2. 三个根本差异（修修补补解决不了的那种）

### A. 缺"交付物"这一层
工作台所有产物都是**工作过程中的中间件**（md 正文、json 行表格）。现实流程的关键动作是
**把一份符合公司模板的文档交给流程系统**。缺的是一条固定链路：

```
结构化数据 → 模板渲染 → 预览/编辑 → 导出成文件 → 上传流程系统 → 回填单号与时间
```

没有这条链路，"工作台里做完了"和"流程上提交了"永远是两件事，用户最终还是得手工写文档 ——
而这恰恰是工作台想省掉的那部分工作。

### B. 方案阶段的数据结构不对
你的原话是"方案主要描述**需要修改或新增什么后端接口**，**前端需要新增或修改哪些页面**"。
这天然是**两张清单**（可逐行增删改），不是一篇文章。现在它们被写进 `draft.md` 的自由文本里，
后果是连锁的：

- 人改不动（改一个接口要去长文里找）
- AI 无法增量维护（只能整篇重写）
- 下游引用不了（开发阶段不知道"我负责哪个接口"，提版阶段汇不出"本次新增 N 个接口"）
- 与现实流程系统的模板对不上（模板要的是字段，不是散文）

### C. 流程没有卡点，也没有回执
现在阶段可自由切换，`status` 只有 `active/paused/done`，`requirement.json` 里没有单号字段。
现实流程是**串行且有准入**的：方案没上传，开发不该开始；自测没过，提版不该提；提版单没提交，
需求不算完。工作台现在**无法表达"这一步到底提交了没有"** —— 这会让状态撒谎，
而状态撒谎比没有状态更糟。

## 3. 目标流程（带准入 / 准出 / 回执）

| 步骤 | 谁做 | 准入（前置） | 产物 | 准出（完成判定） | 给下游什么 |
| --- | --- | --- | --- | --- | --- |
| 0 需求接收 | 需求方上传 / 开发确认 | — | `parsed/vN.txt` + `documents[]` | 标记**正式下发版**并签收 | 供功能点分析 |
| 1 功能点分析 | 开发（可调） | 有正式下发版 | `featurePoints`（含分块/分派人） | 点数与分派冻结（可再改，改动留痕） | 供方案分析 |
| 2 方案分析 | 各开发本人 | 有分派到我的功能点 | **`apis.json`（后端接口清单）+ `pages.json`（前端页面清单）** + `impact.json` + `tasks.json` | 每人清单齐、任务有工时 | 供方案文档渲染、开发执行 |
| 3 方案文档 | 各开发本人 → 主导者汇总 | 步骤 2 完成 | 模板渲染的 `方案文档`（+ `汇总`） | **定稿冻结 + 导出 + 回填流程单号** | 供开发依据、供项目留档 |
| 4 开发 | 各开发本人 | 方案已提交（有单号） | `changes.json` / `commits.json` | 全部任务 `done`，变更均挂 `taskId` | 供自测、供提版汇总 |
| 5 简单自测 + 报告 | 各开发本人 | 开发任务完成 | `selftest.json`（明细）+ **`自测报告`（模板）** | 明细无 `pending`/`fail`，报告有结论 | 供提版单"测试情况" |
| 6 提版 | 开发/主导者 | 自测报告完成 | `release.json` + **`提版文档`（模板）** | **导出 + 回填提版单号 → 需求置"已完成"** | 流程结束 |

关键点：**每一步的"完成"都要有一个不可伪造的事实**（回执字段 / 定稿时间 / 汇总统计），
而不是一句"我觉得差不多了"。

## 4. 改动点清单

### P0 —— 不做这三件，流程仍然走不通

1. **方案阶段新增两张结构化清单**（改动最小、收益最大，直接复用 `STAGE_BLOCKS` 那套行表格 UI）
   - 新增 `apis.json`：`{ point, taskId, name, method, path, change: '新增'|'修改', request, response, note }`
   - 新增 `pages.json`：`{ point, route, name, change: '新增'|'修改', blocks, interaction, note }`
   - 难点说明：`方案` 阶段**目前不在 `STAGE_BLOCKS` 里**（它是 preset：`draft.md/impact.json/tasks.json/design.json`），
     所以要么把这两块做成方案页的第四个/第五个 preset 区块，要么把方案阶段并入 `STAGE_BLOCKS`。
     **建议前者**：改动局部、不动现有方案页的定稿/版本快照逻辑。
   - 同时改 `stagePrompt`：要求 AI **先出这两张表，再据此写 `draft.md`**（正文变成清单的叙述版，
     而不是清单藏在正文里）。
   - 「路径待确认」要成为**合法值**（没有绑仓库时 `path` 留空 + `note` 写清假定的技术栈）。

2. **模板 + 渲染 + 导出**（三份模板：方案文档 / 自测报告 / 提版文档）
   - 新增 `TEMPLATES`（内置默认 + 允许 `Pipeline/_templates/<名>.md` 覆盖）：
     *（已过时：最终落在**工作台级** `templates/<阶段>/`，走宿主 op `readTemplate`/`writeTemplate`。）*
     模板 = 段落顺序 + 占位符，占位符从结构化数据取。
   - 新增 `renderDoc(kind, data)`：纯函数，输入结构化产物 → 输出 markdown。**必须有断言**（模板占位符不得留空值）。
   - 新增预览区块：「生成文档」→ 页内预览可编辑 → 确认后写盘（`方案/<人>/方案文档.md` 等）。
   - 导出：宿主半边新增 op（如 `exportDoc`），用 node 的 `zlib` 生成**真正的 .docx/.xlsx（deflate）**并落到
     `Pipeline/<阶段>/交付/`，用户在资源管理器里直接拖进流程系统；同时提供客户端"复制全文"（可直接粘进富文本）。
     *诚实备注*：客户端半边是无构建的 classic script（只有宿主给的 `react`），不能用 npm 库；
     要 .docx 就得在宿主半边做（可行），或手写 stored 模式的 zip（可行但脆弱）。**先做 md + 复制，.docx 作为第二步。**

3. **交付回执字段**（`requirement.json` 扩展，连带改宿主 `EMPTY_REQUIREMENT` + 客户端读写 + 自检 + `storage-format.md`）
   *（**已取消** —— 你定了"只负责文档生成"，不碰共享元数据。）*
   - 新增 `deliveries: { design: { docNo, at, by, file, note }, test: {...}, release: {...} }`
   - UI：每个阶段页一块「提交记录」小表单（单号 / 时间 / 提交人 / 附件名），**未填写时下游显式提示"上游未提交"**。
   - 这一条同时解决差异 C：有了回执，"提交了没有"就是可读的事实。

### P1 —— 让流程真的顺起来

4. **阶段门禁（只提示，不硬拦）**：`stageGate(stageId)` 依据上游产物存在性 + 定稿 + 回执，
   返回「可开始 / 缺什么」。阶段卡片显示红黄状态。**不要直接禁用按钮** —— 现实中总有例外，
   硬拦会逼用户绕过工具（这是你自己说过的：界面看不见和不存在对用户是同一件事，状态不能撒谎）。
5. **自测报告成型**：`selftest.json` 保留明细行，新增 `自测报告.md`（范围/环境/结果汇总/未测与风险/结论），
   由 `selftest.json` + `测试/cases.json` 的 `result` 自动汇总。明确"自测"归属：建议**报告落在「开发」阶段**，
   「测试」阶段只做接口级补充验证（与刚写死的 `STAGE_RULES.test` 一致）。
6. **提版文档自动汇总**：`changelog.md` 从 `changes.json`（按 `taskId` 归并到功能点）+ `commits.json` 生成，
   缺项（有任务没有变更记录、有变更没有 commit）**列成待补清单**，而不是静默通过。
7. **状态收敛**：提版回执填写后，引导把 `status` 置 `done`；`done` 的判定条件写进提示，
   不允许只靠手点（避免"状态撒谎"）。

### P2 —— 让多人协作和外部系统对齐

8. **角色**：`identity` 现在只有一个 `name`（浏览器本地 + `~/.dsh`）。扩展 `role`（需求方/开发/主导者/测试），
   影响可编辑范围（现在只按"是不是我的按人管线"判定）。需求方需要能上传文档并签收。
9. **仓库绑定**：`requirement.json` 增 `repo: { url, branch, stack, modules }`。
   绑定了就按"改哪个方法"写方案，没绑定（**当前 CRM 需求就是这种**）就按"需要新增什么方法"写 ——
   现在这个判断只存在于提示词里，应该变成显式字段驱动的分支。
10. **通知**：沿用已有 `raiseNotice`，补三类：方案已提交 → 通知开发/主导者；自测 fail → 通知本人；
    提版已提交 → 通知全组。
11. **需求文档分级**：`documents[]` 增 `official: true` 与 `sourceBy`（哪个老师给的），
    `v1.1.txt` 这类版本要能一眼看出"哪版是准的"。

## 6. 一句话结论（当时写的，仍然成立一半）

工作台的**中段很强、两头是空的**：需求解析与功能点管理已经能用，方案正文也能出；
但**方案的结构化（接口/页面清单）、交付物的模板化（三份文档）、流程的回执化（单号与卡点）**
这三件没有，导致它现在是个好用的"思考工具"，还不是一个能替代现实流程的"工作系统"。

> 结算：第一件**已经补上**，第二件补了 1/3（方案文档；自测报告与提版文档待做），
> 第三件**按你的范围决定不做**。所以现在它是「能产出可交付的方案文档、但不管流程提交」的工具。
