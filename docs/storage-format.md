# 存储格式与协同规范

多人用 git 共享同一条管线的信息时，**存储格式就是并发模型**。这份文档定义格式，
并说明每一条规则是为了避免哪种冲突。

---

## 0. 一条规则

> **同一份数据只能由一个人写；不同人写的东西必须落在不同文件。**

git 的冲突判定是「两个分支改了同一个文件的同一处」。所以只要满足上面这条，
同一个需求的并发开发就不会产生冲突 —— 不需要任何锁、合并工具或自定义 merge driver。

反过来说，**把多人各自维护的数据塞进同一个文件，就是在制造冲突**，
无论用数组、对象还是别的结构。

---

## 1. 现状的问题（**旧格式**，已迁移；这一节解释"为什么要改"）

当前格式是「一个需求一个文件夹，大部分数据塞在 `requirement.json` 里」：

```
<reqId>/
├── requirement.json     ← ★ 所有人写这一个文件
└── 需求/ 方案/ 开发/ 测试/ 提版/
```

`requirement.json` 里有七类数据，**编辑者根本不是同一个人**：

| 字段 | 谁改 | 冲突风险 |
|---|---|---|
| `title` / 三个日期 / `status` | 谁都可以，频率低 | 低 —— 两人同时改同一个是**真实分歧**，应该让人来合 |
| `developers` | 谁都可以，频率低 | 低 |
| `featurePoints`（数组） | 谁都可以新增 | **高** —— 两人同时新增 = 改同一处 |
| `clarifications`（数组） | 谁都可以追问/回答 | **高** —— 问答天然是两人分别写的 |
| `documents`（数组） | 通常一个人 | 中 —— 版本记录追加 |
| `currentDeveloper` | **每个人各自** | **✗ 必然冲突** —— 我的视图选择凭什么影响你 |
| 按人的管线进度 | 只有本人 | **✗ 必然冲突** —— 两个人同时推进各自的阶段 |

两个额外问题：

- **读-改-写会静默丢数据。** 即使没有 git 冲突（比如同一台机器上两个浏览器），
  「读整个文件 → 改一个字段 → 写回」也会把别人的改动覆盖掉。
- **`currentDeveloper` 语义就是错的**：它是「我正在看谁的管线」，
  是本机视图状态，不是需求的数据。

---

## 2. 目标格式

按「谁写」切分文件。**目录名即所有者。**

```
docs/requirements/
├── templates/{方案,测试,提版}/          用户提供的模板（公共，很少改）
└── <reqId>/                             一条需求；归档与否只看 requirement.json，
                                         目录位置永远不变，不会搬进历史区
    ├── requirement.json                 ← 共享标量，只此一个文件
    ├── feature-points/<pointId>.json    ← 一个功能点一个文件
    ├── clarifications/<qaId>.json       ← 一条问答一个文件
    ├── documents/<version>.json         ← 一条版本记录一个文件
    ├── pipelines/<developer>.json       ← 每人一份，只有本人写
    └── Pipeline/                        ← 管线相关的一切都收在这里
        ├── 需求/                        公共阶段
        │   ├── source/<version>-<原名>.docx  上传的原件
        │   ├── parsed/<version>.txt          解析出的正文
        │   └── analysis/<version>.md         AI 对这一版的分析（页面显示的就是它）
        ├── 方案/<developer>/            按人
        ├── 开发/<developer>/            按人
        ├── 测试/<developer>/            按人
        └── 提版/                        公共阶段
```

需求文件夹的根部**只放数据文件**；所有管线产物（含五个阶段目录）都收在 `Pipeline/` 下。
这样打开一个需求文件夹，谁是元数据、谁是产物一眼可辨。

### `Pipeline/需求/analysis/` —— 一版文档两个文件：分析 + 功能点

需求文档导入后，**页面上给人看的不是解析出的正文，而是这份分析**。原文照旧留在
`parsed/<version>.txt`，只是退到「查看原文」后面按需展开。

```
analysis/<version>.md            给人读的分析（Markdown）
analysis/<version>.points.json   给工作台读的功能点（JSON，每条带 group 分块）
```

| 规则 | 说明 |
|---|---|
| 路径 | `analysis/<version>.{md,points.json}`，版本号与 `parsed/<version>.txt` 用**同一个 slug 规则** |
| 谁写 | 任何人（需求是公共管线）；一版一份，重跑就是覆盖自己那一份 |
| 判定「分析过没有」 | **文件在不在**，不另存状态字段 |
| 分析陈旧 | 不记录时间戳比对；版本换了就是另一个文件，旧分析不会冒充新文档的结论 |
| 删除 | 删一版文档时**这两个文件一起删** —— 留着一份没有文档的分析，页面会拿它当这一版的结论，而没人能再核对它说的是哪份文档 |
| 重跑 | 已有分析时指令要求**在现有内容上继续优化**，不是从零重写（人的补充会留在里面） |

四条刻意的约束：

1. **一版一份，而不是「文档一份分析」。** 换了文档就必须换文件 —— 否则 `v1.1` 改正了
   `v1.0` 里写错的东西，页面还会拿 `v1.0` 的结论当现状。这同时也让「这一版分析过没有」
   变成一个**文件存在性判断**，不需要任何索引。
2. **功能点是另一个文件，不是分析正文里的一段 Markdown。** 功能点要**机读**
   （工作台拿它自动填需求页），从散文里正则抠列表是那种「今天能跑、明天就错」的做法。
   每一条带 `group`（需求分块），页面按它显示成两级树 —— 详见下面
   `feature-points/<pointId>.json` 一节。
   合并规则：**同名（忽略大小写与空白）即同一个功能点，已存在的一律不动**，
   唯一的例外是补 `group`（它还没有分块时才补）——
   人可能已经改了名字、派给了人、在方案里引用了它，重新分析不该把这些抹掉。
   所以同一个版本分析两次，第二次补进 0 个、补分块 0 个，不会让列表翻倍。
3. **不记「谁分析过、什么时候分析的」字段。** 那又是一份要「读-改-写」的共享元数据，
   而且它回答不了任何真问题：分析内容是分析时间最好的注解。
4. **指令只准写这两个文件。** 「让 AI 分析」走的是对话通道（同方案页，见
   `designPrompt` 一节），指令里写死了产物路径，并**明确禁止改 `parsed/`、
   `requirement.json` 与其它版本的分析** —— AI 顺手去"修正"解析出的原文，会让导入的
   正文和分析互相打架，而这两份文件都无法从对方恢复。
   功能点由工作台自己读那个 JSON 去填，AI**不要**去改 `requirement.json`。

**为什么原文不再排在最前面。** 一份几万字的 `.docx` 解析出来就是一大片没有结构的文字，
它回答不了读者真正的问题（这份需求要做什么、动到哪些东西、哪里有坑、哪里还没说清）。
把它摆在最前面，等于每次导入都让人自己去读一遍并自己形成结论。「导入即分析」把这一步
交给 AI，原文仍在，只是回到它该在的位置：**核对用的证据**。

#### 「差异异常」提示：两版对比顺带能抓到的上传错误

两版对比除了给人看差异，还回答一个机器更容易答的问题：**这次的差异合不合常理**。

| 现象 | 判定 | 提示 |
|---|---|---|
| 版本号跳了一大截（大版本变了）而正文几乎没动 | `jump` | 可能上传错了文件（或同一份传了两次）—— 核对原件，必要时删掉重传 |
| 正文改了很多而分析几乎没动 | `stale` | 分析可能是在旧正文上做的 —— 对右版点「继续优化」 |

两个阈值都刻意保守（正文变化 ≤2% 才算"没动"、≥25% 才算"改了很多"），并且
`stale` 只在**两版都有分析**时才判 —— 分析缺失是另一件事（先去跑分析），
混在一起说会让人以为分析写坏了。误报一次，人就不再看这个提示了。

### 归档 = 标记，不搬目录

归档**不是**「把文件夹搬进 `_history/`」，而是把 `requirement.json` 的 `archivedAt`
写成非空时间戳。已归档的需求永远待在 `docs/requirements/<reqId>/` 原地。

| 规则 | 说明 |
|---|---|
| 判定 | `archivedAt` 非空串即已归档。**目录位置不参与判定** |
| 写入 | **写一次，永不覆盖**。已归档就直接返回，不更新时间戳 |
| 兜底 | `requirement.json` 缺失或损坏 → 一律当**活跃**。宁可多显示，不可静默吞掉一条需求 |
| 语义 | **软归档**：已归档的需求仍可编辑、仍能被恢复。恢复只是清空 `archivedAt` |

为什么不用 `status` 表达归档：`status` 已经在跑 `active / paused / done` 三态，
归档是与生命周期正交的维度，混进同一个字段会互相覆盖。

**为什么这条规则值得占用一整节** —— 搬目录的代价有三层，而且都不是理论问题：

1. **git 历史断裂。** git 不存 rename，整目录移动会被记成「一批删除 + 一批新增」，
   `git log -- <path>` 从此接不上，只能靠 `--follow` 一个个文件去追。
2. **无法靠约定避免的硬冲突。** 甲归档目录的同时乙在改目录里的文件，git 报
   `CONFLICT (modify/delete)`。改成标记后，甲只改 `requirement.json`、乙只改自己的
   阶段产物 —— 路径不相交，merge 干净。这是从前唯一躲不掉的冲突。
3. **Windows 上会直接失败。** 目录里只要有人开着 `.docx`（Word/Excel），或者杀软
   正在扫描，`rename` 就抛 `EPERM`/`EBUSY`，归档当场失败（Linux 无此问题）。

「写一次，永不覆盖」也不是加固而是**正确性前提**：归档后需求留在原地，逾期扫描每天
都能再看见它一次；少了这个判断，每开一次工作台就会把所有已归档需求的时间戳重刷一遍，
git 里天天多出一行冲突。两个人同一天各自触发自动归档时，第二个人也不会覆盖第一个人的记录。

**这条规则的唯一代价**：活跃目录会永久增长，不再有「搬走」这个泄压阀。列表靠扫描 +
读标记，所以**绝不能为了提速加一个全局索引文件**（见第 5 节）。

### 删除 = 整个文件夹一起删（和归档是两件事）

`deleteRequirement` 是**唯一不可逆**的 op：`rm -r docs/requirements/<reqId>/`。
它存在的理由是"一个需求的一切都在它的文件夹里"这条设计本身 —— 文档原件、解析出的正文、
每一版分析与功能点清单、方案、测试记录，全在同一个目录下。

| 规则 | 说明 |
|---|---|
| 与归档的区别 | 归档只是**一个标记**，随时能恢复；删除**没有任何地方还留着副本**。两者不是一个动作的强弱两档，是两件事 |
| 不复用 `remove` | `remove` 明确拒绝删需求文件夹本身（`workbench/bad-path`），那条守卫**保留不动**：删里面的某个文件是日常操作，删掉整条需求不该由它顺手完成 |
| 二次确认在客户端 | 宿主只做那个不可逆的动作，不假装自己知道用户点了什么。确认屏在本机（`RequirementChips`），点了之后整条菜单被换掉 —— 原先那些按钮此刻**根本不在 DOM 里** |
| 不存在就报错 | `workbench/not-found`。静默"成功"会让人以为删掉了，而其实还在 |
| 编号先校验 | 路径拼接前过 `REQUIREMENT_ID_PATTERN`，`../../etc` 这类一律 `workbench/bad-id` |
| 顺带清掉指向它的本机状态 | 通知表（`clearNotice`）与"我在看谁"的映射。它们按需求编号记，留着不报错，但都是死引用 |

**宿主半边为自检多导出了一个 `__ops`**（`deleteRequirement` / `removePath` / `locateRequirement`）：
删除的失败方式是"删了一半"或"该拒绝时没拒绝"，两种都不会在页面上报错，
所以 `tools/verify.mjs` 要在临时目录上真的调用它，而不是只对着源码做正则。

### `requirement.json` —— 只放共享标量

```jsonc
{
  "schema": 2,
  "id": "XQ20260810-0031",
  "title": "客户经营信息优化",
  "status": "active",              // active | paused | done
  "createdAt": "…", "updatedAt": "…",
  "archivedAt": "",
  "releaseDate": "2026-10-10",     // 提版 < 封板 < 上线
  "testFreezeDate": "2026-10-14",
  "goLiveDate": "2026-10-18",
  "developers": ["张三", "李四"],   // 名单；按人数据的文件名由它决定
  "leadDeveloper": "张三",         // 主导者；空串 = 取名单里的第一个人
  "overdueNoticeAt": ""            // 遗留字段：逾期通知已挪到本机（见第 3 节）
}
```

**保留在单文件里的理由**：这些都是「整个需求只有一个值」的标量，改动频率低。
两个人同时改同一个标量是**真实分歧**，应该由人来解决 —— 这正是 git 冲突该出现的地方。
把它们拆成文件只会掩盖分歧。

**`currentDeveloper` 不在其中**：它属于第 3 节。

### `feature-points/<pointId>.json`

```jsonc
{
  "id": "fp-3f9a…",          // 生成即固定，等于文件名
  "name": "客户信息导出",
  "group": "客户主数据",       // 需求分块（可选）；空/缺省 = 未分组
  "assignee": "张三",         // 空串 = 未分派
  "note": "",
  "source": "v1.0", "sourceVersion": "v1.0",   // 出自哪一版文档（AI 拆出来的才有）
  "createdAt": "…", "updatedAt": "…"
}
```

**为什么一文件一条**：两个人同时新增功能点，落在两个新文件里 —— git 只会把两个
新文件都加进来，不存在冲突。放进数组则必然改同一处。

**`id` 用随机 id 而不是序号**：序号需要读现有最大号，那又是一次「读-改-写」竞争。

#### `group` —— 功能点按需求分块（树形的第一级）

上百个功能点平铺在一屏里，"客户合并"和"回款逾期冻结"挨在一起，读者没法判断自己看的是
哪一块、有没有漏搬某一整块。所以功能点带一个 `group`（需求分块），页面按它显示成两级树：
**分块 → 功能点**。

| 规则 | 说明 |
|---|---|
| 来源 | AI 分析时按文档自己的章节/模块写；同一模块必须写**一模一样**的字符串 |
| 存在哪 | 就存在功能点上，**不另建分块注册表** —— 两份数据就得同步，而同步迟早不一致 |
| 改名 | 把这一块所有点的 `group` 一起改，一次写盘 |
| 缺省 | 没有 `group` 时，从点名推前缀（`deriveGroupName`），但**该前缀要在清单里出现两次以上才算一块**（孤例不成块）；推不出来就是**未归类**，显示成树根下不带块头的散条 |
| 「未分组」不作为一个块 | 下拉里没有「未分组」这一项，树上也没有叫这个名字的块头 —— 它不是一个"地"，只是"还没归类"。但**未归类的点仍然显示**：界面看不见和不存在，对用户是同一件事，而数据其实还在 |
| 下拉里**永远有一个 `value=""` 的隐藏占位项** | 这是让下拉不说谎的关键：value 匹配不上任何一项时（一块都还没建、或这条点还没归类），浏览器会把**第一项当当前值显示出来**，而用户点它时 value 没变化、`change` 不派发 —— 表现就是"这一格显示着 `+ 新分块`，点了却没反应"（用户两次报的"新分块加不了"都是它）。它 `hidden`：列表里不出现，因此不会多出一个「未分组」选项 |
| 新建分块在**新增区**的下拉里 | 两处的下拉**故意不一样**：功能点**行**上那个只列**已经建好的分块**（那是"归类"，不是"造分类"）；只有底部**新增区**那个多一项 `+ 新分块`。选中它就把 value 换成哨兵值 `NEW_GROUP`，于是**分块下拉与分派人下拉之间**长出一个取名框 |
| 分块与功能点**一起**建出来 | 名字只在点【新增功能点】那一刻才读（`groupForAdd`）：分块和它的第一条点在同一次写盘里出现。反过来"选中下拉就先建块"会留下有块没有点的空块，中途放弃还得再删一次 |
| 哨兵值 `NEW_GROUP` 不落盘 | 它只是控件内部的值。选了新建却没起名字时**拒绝新增**并提示（Esc 放弃），不静默落到未分组 —— 那等于把用户明确表达过的"我要新建一块"丢掉 |
| 顺序 | 分块按**首次出现顺序**，不排序：文档的模块顺序本身是信息 |
| 层级 | 只有两级。需求文档的章节结构是两级的，而"一个功能点 = 一件可独立交付的事"这个粒度上，更深的层级没有意义 |

**合并时唯一会被"补写"的字段就是 `group`**：同名的点其余字段一个字不动（人可能已经
改名、派了人、在方案里引用了它），但如果它还没有分块、而这次分析给了，就补上。
这条是让树形在**老数据**上生效的自动化手段 —— 否则只能靠人一个个手填。
补写是幂等的：同一份分析跑两次，第二次补 0 个。

### `clarifications/<qaId>.json`

同样一文件一条。问答常常是「甲提问、乙回答」两个人分别写的：
一条一个文件时，两人改的是同一个文件但**不同段落** —— 而更稳的做法是**不原地改**：

- 提问写 `<qaId>.json`（`answer` 为空）
- 回答时**新增** `<qaId>.answer.json`，不改原文件

这样连「同一文件不同段落」都不需要 git 去合并。

### `pipelines/<developer>.json`

```jsonc
{
  "developer": "张三",
  "stages": { "design": "active", "develop": "pending", "test": "pending" },
  "updatedAt": "…"
}
```

**只有本人写自己的那份。** 文件名由 `requirement.json` 的 `developers` 决定，
所以两个人推进各自阶段时改的是不同文件。

**文件名安全**：开发人员姓名要做文件名转义（去掉 `/ \ : * ? " < > |` 与首尾空格、
`.` 开头），姓名本身存在文件内容里。**改名会引起文件重命名** —— 这是已知代价，
换人时应当视为一次独立提交。

### 阶段产物

- **公共阶段**（`Pipeline/需求/`、`Pipeline/提版/`）：直接放在该阶段目录下。
- **按人阶段**（`Pipeline/方案/ 开发/ 测试/`）：每人一个子目录。
  生成的文件天然不会互相覆盖。

阶段目录一律建在 `Pipeline/` 之下（宿主半的 `PIPELINE_DIR`）。**这个层级一旦定下就
不要再调整** —— `requirement.json` 里 `documents[]` 的 `file` / `textFile` 是**相对需求
文件夹**的路径（例如 `Pipeline/需求/source/v1-0-原件.docx`），改动层级会让已持久化的
路径失效。整目录归档不会（相对路径依然成立），但层级调整会，而且已归档的需求不会被
重新读一遍来"顺手修好"。所以层级迁移必须配一个**同时扫描全部需求**的重写脚本。

### `Pipeline/方案/` —— 方案阶段的产物

方案是**按人分开**的管线，一个开发人员一套文件，各写各的；在此之上还有一份**共享的汇总**：

```
Pipeline/方案/
├── 汇总.md              ← 共享的那一份，由主导者写，不属于任何人
└── <developer>/         ← 按人，每人一套
    ├── draft.md          方案正文（Markdown）
    ├── versions/v1.md    正文的历史快照（留档用，不影响正文）
    ├── impact.json       影响面分析
    ├── tasks.json        任务拆分
    ├── apis.json         后端接口清单（要改 / 新增哪些接口）
    ├── pages.json        前端页面清单（要改 / 新增哪些页面）
    ├── 方案文档.md        ← **生成物**：按模板渲染出来的可交付文档（导出物，不要手改）
    └── design.json       定稿时间
```

`apis.json` / `pages.json` 是**结构化清单**，不是散文：方案要回答的现实问题就是
"后端要改或新增哪些接口、前端要改或新增哪些页面"，写成一篇长文之后人改不动、
AI 只能整篇重写、下游也引用不了。它们的形状与其它产物同一套约定：

```jsonc
// impact.json
{ "schema": 1, "developer": "张三",
  "modules": "一行一个受影响模块/文件", "risk": "low|medium|high",
  "rollback": "出问题怎么退回", "dependencies": "依赖与前置条件", "updatedAt": "…" }

// tasks.json —— 任务记住来源功能点，这是「需求 → 方案」两层的连接点
{ "schema": 1, "developer": "张三",
  "tasks": [{ "id": "…", "pointId": "fp-…", "title": "…", "estimate": 2, "done": false }],
  "updatedAt": "…" }

// design.json
{ "schema": 1, "developer": "张三", "confirmedAt": "", "updatedAt": "…" }

// apis.json
{ "schema": 1, "developer": "张三",
  "items": [{ "pointName": "客户建档表单", "taskNo": "T04", "name": "客户查重预检",
              "method": "POST", "path": "/api/customer/dedup/check", "change": "新增",
              "request": "name、uscc", "response": "hits[]", "note": "" }],
  "updatedAt": "…" }

// pages.json
{ "schema": 1, "developer": "张三",
  "items": [{ "pointName": "客户建档表单", "taskNo": "T03", "name": "客户列表页",
              "route": "/customer/list", "change": "修改", "blocks": "筛选区、列表",
              "interaction": "失焦即预检", "note": "" }],
  "updatedAt": "…" }
```

**「路径待确认」是合法值**：没有可改的既有工程（技术栈未定、手上没有代码库）时，
方案就只能说"需要新增哪些接口"。编一个像真的路径比留空更糟 —— 下游会照着它去写代码。

`方案文档.md` 是**生成物**：文件头一行 HTML 注释写着用了哪份模板、什么时候生成、读了哪些数据源，
重新生成直接覆盖。要改内容就改清单或正文，不要改它。

### 模板：`templates/<阶段>/`（工作台级，不在需求文件夹里）

```
<工作台根>/
└── templates/
    ├── 方案/方案文档.md
    ├── 测试/…
    └── 提版/…
```

模板是**一套全工作台共用**的，所以放在工作台根而不在每条需求里（这三个目录由宿主的
`ensureLayout` 按 `TEMPLATE_DIRS` 建好）。它不在需求文件夹内，客户端读不到 ——
读写走宿主 op `readTemplate` / `writeTemplate`（这两个 op 是**开机注册**的，
宿主没重启时客户端会收到 `unknown-op`，界面据此提示"重启一次 DSH"，而不是静默回落）。

`writeTemplate` **拒绝覆盖**已存在的文件：它唯一的用途是把内置模板摊出来给人改，
一次点击抹掉别人按公司模板改好的文件是不可逆的损失。

占位符语法只有三种（**刻意不支持嵌套循环**，模板要给人手写）：

```
{{path}}                    标量；取不到值 → 渲染成「（待补：path）」并汇总成清单
{{#each path}}…{{/each}}     循环（行里自动带一个 1 起的 {{index}}）
{{#if path}}…{{else}}…{{/if}}  条件（空串 / 空数组 / 0 都算「没有」）
```

列表项里的空字段**留空**（表格的空单元格就是没写），文档级字段缺失才显示「待补」——
两条规则合起来的效果是：真正的缺口会跳出来，而正常的空格不会把文档刷满提示。

**目录名即所有者**，规则见下面 `pipelines/<developer>.json` 一节的转义说明。

五条刻意的约束：

1. **方案页一个字都不写 `requirement.json`。** 它是纯按人管线：两个人同时写各自的方案，
   路径不相交，merge 干净。契约自检里有一条断言直接扫源码，禁止方案页出现
   `writeRequirement`。
2. **快照序号从目录里已有的文件名推**（`v1.md` → `v2.md`），**不建索引文件**。
   索引文件就是那份会「读-改-写」的东西，正是第 5 节第一条要顶住的诱惑。
3. **状态以真实产物为准。** 「分到功能点的人，方案算进行中」只是**还没有方案文件时的
   兜底**；一旦读得到方案目录，状态就来自文件本身（有内容 = 进行中，`confirmedAt`
   非空 = 已审核）。少了这条，方案页写完也不会让管线变绿，用户会以为没保存上。
4. **「让 AI 出方案」走的是对话通道，不是插件调模型。** 插件只负责把需求编号、目标
   文件路径、产物 JSON 形状拼成一段指令，送进当前会话（平台通道
   `ctx.sessions.scope(id).conversation.send`）；对话里的 AI 用它自己的文件工具读需求、
   写文件。所以这段指令就是**插件与 AI 之间唯一的契约** —— 少写一个路径，AI 就得猜。
   既然是契约，**阶段之间"该怎么用力"也要写进去**（`STAGE_RULES`）：光有路径与形状，
   AI 会按最省事的默认去写。例：测试阶段明确「不做功能点的完整详细测试、代码质量由 AI
   自己读代码检查、用例只做简单的接口测试（一个接口 1–2 条）」—— 不写这条，它就会给每个
   功能点穷举边界，产出几百条没人会跑的用例。
5. **汇总只有一份，而且是共享的。** 它读**所有**人的方案，产出一份给主导者看的整体
   开发概念（各人对照、分歧、覆盖缺口、依赖顺序、投入合计、风险）。写者是**主导者
   一个人** —— 它就是第 0 节说的「真实分歧应该由人来解决」那一类：一份文档一个 owner。
   它**不参与按人状态推导**：某人写没写方案，和全队汇没汇总，是两件独立的事。
   它的「更新于」直接从文件系统的修改时间取，不另建元数据文件。

**目录名不含点号**：转义会把点号换成下划线。这不是洁癖 —— 共享的汇总文件叫 `汇总.md`，
如果某个开发人员就叫「汇总.md」，他的目录会和这份共享文件同名，而**文件和目录不能同名**，
汇总从此写不进去。保证目录名不含点号，这类撞名就**不可能发生**，而不是"大概不会发生"。
契约自检对 `汇总.md` / `a.b.c` / `..x..` 这类名字逐个断言过。

**已知代价**：姓名转义仍会撞名（`张三` 与 `张 三` 落到同一个目录）。这与
`pipelines/<developer>.json` 是同一个代价，处理方式也一样：文件名里记着姓名，打开
文件能看出是两个人。

### 开发 / 测试 / 提版的产物

这三个阶段的产物由客户端的一张**声明表**（`lib/client.js` 的 `STAGE_BLOCKS`）驱动 ——
页面、落盘路径、状态推导、给 AI 的指令全部从那张表生成，所以它们的布局是同一套规则：

```
Pipeline/
├── 开发/<developer>/          按人
│   ├── changes.json           变更清单  { items: [{ taskId, target, note, done }] }
│   ├── commits.json           提交记录  { items: [{ hash, message }] }
│   └── selftest.json          开发自测  { items: [{ item, result, note }] }
├── 测试/<developer>/          按人
│   ├── cases.json             测试用例  { items: [{ name, expected, result }] }
│   ├── runs.json              执行结果  { items: [{ at, passed, failed, note }] }
│   └── defects.json           缺陷跟踪  { items: [{ title, severity, status }] }
└── 提版/                      共享（公共管线）
    ├── release.json           { version, releasedAt }
    ├── changelog.md           变更日志
    └── notes.md               发布说明
```

JSON 产物的统一形状是 `{ schema: 1, developer?, items: [...], updatedAt: "…" }`
（`release.json` 用几个标量字段代替 `items`）。

**为什么这些文件里可以有数组。** 第 1 节批评过「把多人各自维护的数据塞进同一个数组」，
但那条批评针对的是**共享文件**。这里的每个 JSON **只有一个写者**（按人阶段是本人，
提版是公共管线但它是「一份文档一个 owner」那一类），所以 `items` 数组不会变成冲突热点 ——
真正要避免的是「`requirement.json` 里的 `featurePoints`」那种**多人往同一个数组里加**。

**【执行】只出现在能被"跑一遍"的行上。** 开发页的每个任务、测试页的每条用例都有一个
【执行】（测试那一块里它挨在【删除】前面）；`runs.json` / `defects.json` 没有 ——
执行记录与缺陷记录不是"跑的对象"。哪些块有，由 `STAGE_BLOCKS` 里那行 `execute` 声明，
渲染器不认识阶段名。

两个阶段的【执行】都会让 AI **把结果落回这些文件**，而不是只在对话里说一句：

| 【执行】 | 读 | 写 |
|---|---|---|
| 开发页：一个任务 | 这个人的方案五件（draft / impact / apis / pages / tasks） | `changes.json` 每改一处追加一行；`selftest.json` 补自测项 |
| 测试页：一条用例 | 方案（接口 / 页面清单）+ 开发产物（changes / selftest） | 这一条用例的 `result` + note；`runs.json` 追加一条；失败时 `defects.json` 追加一条 |

**用例没有 id**，所以测试的【执行】靠「用例名 + 预期 + 第几条」三者一起定位，指令里要求
AI 对不上或重名时停下来问，不要猜一行去改。（如果哪天用例开始重名到无法区分，就该给
`cases.json` 加一个 id 列 —— 那是格式变更，不是这里能顺手做的事。）

**完成条件**（管线徽标显示「已审核」的依据，写在 `STAGE_DONE` 里，刻意朴素到能在界面上解释）：

| 阶段 | 已审核的条件 |
|---|---|
| 开发 | 变更清单非空且全部勾完，自测项非空且全部通过 |
| 测试 | 用例非空且全部通过，且没有未关闭的缺陷（待修 / 修复中都不算关闭） |
| 提版 | 版本号与发布说明都填了 |
| 方案 | **有内容**且已定稿 |

两条容易被忽略的约定：

- **空的东西不能算完成。** 一份空的方案被点了「定稿」，徽标也不该变绿 ——
  状态说谎最容易被忽略的形式就是「界面上给了个按钮，点一下就绿了」。
  界面上那道按钮同样会禁用，两道守卫缺一不可。
- 只是「写了点东西」不等于完成：写了变更清单但自测没做，就是**进行中**。

### 任务的执行情况：跨层派生，不另存状态

开发页要回答两个问题：**我要做什么**、**哪些还没开工**。答案分散在两处：

| 事实 | 落在哪 | 谁写 |
|---|---|---|
| 要做什么、多少工作量 | `Pipeline/方案/<人>/tasks.json` | 本人（方案页） |
| 实际改了什么、勾没勾完 | `Pipeline/开发/<人>/changes.json` 的 `taskId` 列 | 本人（开发页） |

**执行情况不另存一份状态**，而是从「变更清单里挂在这个任务上的行」推出来：

- 一条变更都没挂 → **未开工**
- 挂了但没全勾完 → **进行中**
- 挂了而且全勾完（或方案页上手工勾了「完成」）→ **已完成**

为什么不把状态存进 `tasks.json`：那就有了两份真相，必须有同步，而同步迟早会不一致 ——
到那时两个页面会各说各话，而且**没有任何报错**。派生出来的状态不可能不同步。

这也决定了两个页面各管一头：**任务的定义归方案页**（那里生成、那里改），
**开发页只负责往上挂证据** —— 任务本身的字段在开发页一个都改不了。

开发页上唯一的动作是每行任务后面的【执行】：它把「实现这一个任务」的指令送进当前对话
（**先弹窗让你改，再发** —— 指令发出去 AI 就动手了，那一步收不回来）。这个动作
**不新增任何存储格式**：指令要求 AI 把改动追加进上面那两个文件（`changes.json` /
`selftest.json`），所以执行完之后，任务状态照旧是从变更清单派生出来的。指令里另外钉死两条：

- `taskId` 必须**逐字**用这个任务的 id —— 挂不上的话页面会一直显示「未开工」，那是界面在说谎；
- `done` 一律先填 `false` —— 勾选是开发者本人的复核动作，不是 AI 的自我评价。

【执行】只给自己那条管线显示（`editable`）：从别人的页面上发起执行，等于用别人的名义去改代码。

「没有任务」有两层，界面上分开说：

- **还没有开工的任务** —— 任务存在，只是没挂任何变更；
- **还没有任何任务的功能点** —— 这条活压根没人拆出来，要去方案页补。后者更危险：
  一个没有被拆成任务的功能点，在开发页上**根本不会出现**，很容易就这么漏掉。

### 编辑权：按人管线看「是谁的」，汇总看「是不是主导者」

方案阶段有**两套互不相同的编辑权**，判定依据不同，所以必须分开实现：

| 对象 | 谁能改 | 依据 |
|---|---|---|
| 某人的方案（正文 / 影响面 / 任务 / 定稿） | **只有本人** | 我在看的这条管线是不是我的 |
| 某人的开发 / 测试产物 | **只有本人** | 同上 |
| 方案汇总（`Pipeline/方案/汇总.md`） | **只有主导者** | 我是不是主导者 |
| 提版产物（`Pipeline/提版/`） | 任何人 | 公共管线，与「需求」同级 |
| 需求层（日期 / 开发人员 / 功能点 / 文档 / 问答） | 任何人 | 公共管线 |

把前两行和第三行混成一个判断会立刻出错：主导者在看**别人**的管线时，按人门禁是「只读」，
可是全队汇总本该由他来改 —— 合在一起就会出现「主导者反而改不了汇总」这种荒唐结果。

### 主导者

`leadDeveloper` 是**共享标量**，按第 0 节的判据它就该待在 `requirement.json` 里：
「谁是主导者」整个需求只有一个值，两个人同时改它属于**真实分歧**，本就该由人来解决。

- **默认是名单里的第一个人**，而且这个默认值是**推导出来的、不写盘** ——
  所以已经存在的需求不需要任何迁移就自动有了主导者。
- **变更只有现任主导者能做。** 这不是为了严格而严格：如果谁都能改，那
  「只有主导者能编辑汇总」就是**空的** —— 任何人先把自己设成主导者就行了。
  **权限的入口必须和权限本身一样紧。**
- 界面上变更是**两段式**（先选人、再确认），不是一个下拉框随手一划就生效；
  不是主导者时按钮仍在，但会说明「只有主导者（X）能变更」。
- **逃生口**：记下的主导者已经不在名单里（被移除了）时，自动回落到名单里的第一个人。
  少了这条，主导者一被移除，方案汇总就**永远没人能改**。移除主导者时也会顺手清掉
  这个字段，不留一个指向陌生人的陈旧值。

## 3. 本机状态一律不能进共享树

**身份**（我是谁）、**视图选择**（我在看谁的管线）和**逾期提醒的已读状态**
都是「本用户」的状态，不是需求的数据。把它们写进 `requirement.json` 会让每个人的
本地操作都去改一个共享文件。

| 数据 | 存放位置 | 理由 |
|---|---|---|
| 我是谁（`name`） | `$DSH_HOME/workbench/identity.json` | 跨项目跟着人走；不进仓库 |
| 逾期提醒何时登记 / 何时已读 | `$DSH_HOME/workbench/notices.json` | 「换个人打开就该不一样」—— 别人打开工作台不该重置我的倒计时，也不该被我的已读状态影响 |
| 我在看谁的管线 | 浏览器本地（`localStorage`，`dsh.workbench.view`） | 纯视图状态，跨机器同步没有意义 |

规则：**凡是「换个人打开就该不一样」的东西，都不能放在 `docs/requirements/` 下。**

### 需求与会话：不绑定

插件**不把需求绑到会话上**。所有 AI 动作（文档分析、出方案、汇总、各阶段产物）都发到
**用户当前正在用的那个会话**里，走平台通道 `ctx.sessions.scope(id).get('conversation').send(text)`。

这条是权衡后的决定，值得写下来，免得以后又想"顺手做一下隔离"：

- **会话归属是用户的，不是需求的。** 人在哪个会话里，就说明他此刻在这个上下文里工作；
  插件把他悄悄切到另一个会话，是替他做决定 —— 而且他会立刻迷失在侧边栏里那一堆
  以需求编号命名的新会话中。
- **「每条需求一个会话」看起来像隔离，实际是会话爆炸。** 建需求建一个、导入文档建一个、
  切回来再建一个，二十条需求之后侧边栏全是空会话，人就不再信任"新建会话"这个动作了。
- **需求之间本来就不会互相污染。** 每条需求的产物都在自己的目录里
  （`docs/requirements/<reqId>/…`），插件发的指令里写的都是**绝对路径** ——
  跨需求串台需要两边同时出错，而会话隔离对此帮不上忙。

**模块之间**的越界是另一回事，那个用子 agent 解决：指令里要求 AI 在只做本模块的子 agent
里干活（`subagentDirective`），因为插件这一层没有「派活给子 agent」的 API ——
能做的最强约束就是把要求写死在指令里，并说清理由。

### 通知表的两条写入规则

```jsonc
// $DSH_HOME/workbench/notices.json —— 每人一份，不进 git
{
  "schema": 1,
  "notices": {
    "XQ20260810-0031": { "raisedAt": "…", "readAt": "" }   // readAt 空串 = 未读
  }
}
```

- **`raisedAt` 由客户端给，不由宿主取当前时间。** 升级前写在共享文件里的旧计时会被
  继承过来 —— 自动归档的 3 天窗口必须跨用户一致，换个人打开工作台不该把倒计时重置。
- **两者都是「写一次，永不覆盖」**（宿主 `raiseNotice` / `markNoticeRead`）。
  少了这条，两个人同一天打开工作台就会各自覆盖对方的时间戳。
- 共享的 `requirement.json` 里那两个旧字段（`overdueNoticeAt` / `overdueNoticeReadAt`）
  **只在宿主还是旧版本时**继续读写；新版本里它们是死的，只在「恢复已归档需求」时
  被清空一次（否则旧值会被当成继承来源重新种进本机通知表，刚恢复的需求立刻又被归档）。

## 4. 兼容与迁移

**归档语义（`_history` → 标记）**：这是已经落地的变更，不是计划。

- 旧版归档 = 把 `<reqId>/` 整个搬进 `_history/`。新代码**不再去 `_history` 找需求**，
  所以旧数据必须搬回工作台根，并保证 `archivedAt` 非空 —— 否则新代码会把它当成活跃需求。
- 迁移脚本：`node tools/migrate-history.mjs`（默认预演，`--apply` 才动磁盘）。
  目标位置已存在同名需求时它**跳过并报错**，绝不覆盖、绝不合并。
- `archivedAt` 字段本身**在旧版就已存在**（那时也写，只是同时搬目录），所以迁移
  通常不需要改任何元数据，纯粹是把文件夹往上挪一层。

**逾期通知的本机化（共享字段 → `notices.json`）**：这是已经落地的变更。

- 旧版把「何时登记提醒 / 何时已读」写在共享的 `requirement.json` 里，于是
  **谁先打开工作台谁写** —— 两个人同一天打开必然改到同一处。
- 新版写进 `$DSH_HOME/workbench/notices.json`（每人一份）。共享文件里的旧值只作为
  首次登记时的**继承来源**，之后不再参与判定。
- 不需要迁移脚本：每条提醒在第一次被本机扫描到时自动落进本机通知表。

**阶段目录收进 `Pipeline/`**：这是已经落地的变更。

- 迁移脚本：`node tools/migrate-layout.mjs`（默认预演，`--apply` 才动磁盘）。
- 它同时**重写 `requirement.json` 里 `documents[].file` / `textFile` 的路径前缀** ——
  这两个字段是相对需求文件夹的路径，层级一变就失效，而且已归档的需求不会有人再去读
  一遍"顺手修好"。这是「路径变更」唯一真正危险的地方：搬目录本身不可怕（相对路径
  依然成立），**改层级才可怕**。

**字段拆目录（`schema` 1 → 2）**：这是尚未实现的计划。

- 读取时**双读**：`schema: 1` 的需求，把 `featurePoints` / `clarifications` /
  `documents` 三个数组当作内存里的数据用；**写入时**升级为 `schema: 2` 的目录结构，
  并把三个数组从 `requirement.json` 里删掉。
- `schema: 1` 的需求继续可用，只是仍然有上述冲突风险 —— 迁移是渐进的，
  不需要一次性改完所有历史需求。

## 5. git 纪律

存储格式只解决「谁写哪个文件」。仓库怎么用，还得有几条约定：

1. **绝不加全局索引文件。** 需求列表靠「扫一层目录 + 读每份 `requirement.json`」得出
   （`listRequirements`）。任何人为了提速加一个 `index.json` / `.workbench-cache`，
   都会把它变成**永久冲突热点** —— 那是唯一的全局共享文件，每次归档、每次新建都要改它。
   归档不搬目录之后活跃目录会长期增长，"加个索引吧"的诱惑会越来越大，这条要顶住。
2. **`*.docx` 按二进制处理。** `.docx` 本身是 zip，git 的 delta 压缩几乎无效，
   每个版本约等于一个完整 blob；不声明 `binary` 还会让 git 去做无意义的文本 diff
   和行统计。数据仓库的 `.gitattributes` 里应有 `*.docx binary` 与 `*.docx -diff`。
3. **`git config core.quotepath false`。** 目录名全是中文（`需求/方案/开发/测试/提版`），
   默认配置下 git 会把它们转义成 `\346\226\271\346\241\210`，`git status` 基本没法读。
   每个开发者本地设一次，或写进仓库说明。
4. **归档不需要单独一次提交了。** 旧方案下「移动 + 改内容」混在一个 diff 里会削弱
   rename 识别，所以要拆开提交；现在归档只有 `requirement.json` 里一行改动，没有这个约束。

## 6. 检查清单

新增任何存储字段前，先问四个问题：

1. **谁写这个字段？** —— 一个人？那它能和那个人的其它数据放一起。
2. **两个人会同时写吗？** —— 会？那必须拆到不同文件。
3. **换个人打开应该不一样吗？** —— 应该？那它不该在这个目录里。
4. **它是「事实」还是「谁先看到」？** —— 「谁先看到」这类字段（例如通知计时）即使
   只被写一次，也会因为「谁先打开工作台」而不确定，天然是冲突源。它属于本机状态，
   不属于共享树。

违反任意一条，就会在协同开发时产生冲突或静默丢数据。

目前共享文件里**没有**已知的违反点：视图选择在浏览器本地，身份与通知计时在
`$DSH_HOME/workbench/`，归档是标记而非目录移动，需求列表靠扫描而非全局索引，
**按人阶段（方案 / 开发 / 测试）的产物全部落在按人目录里、一个字都不写共享元数据**；
跨人的方案汇总是一份**单写者**的共享文档（写者就是主导者）。提版是公共管线，
但它同样是「一份文档一个 owner」那一类：变更是追加上去的历史，不是多人各写一半的现状。
新增字段前请对着上面四个问题过一遍 —— 尤其是第 4 条，它是最容易被忽略的一类。
