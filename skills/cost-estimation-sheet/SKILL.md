# 用成本度量表模板出规模与工作量估算

把一个需求的**功能点**变成三样能给外人看的东西：**规模（FP）→ 开发工作量（人天）→ 四个角色的工时**。
产物必须能落回工作台（机读 JSON）+ 能交出去（填好的 Excel）+ 能进方案文档（一节 Markdown）。

**这个 skill 的难点不在算术，而在三件事：模板哪一格能动、系数与生产率从哪来、哪些数是"推算"而非"文档写的"。**

---

## 1. 铁律（动手前先读完）

1. **只填白色单元格，其余颜色一律不碰。** 模板用颜色划分所有权（见 2.2）。深灰（模板固定）、浅灰（必要时统一改）、绿色（自动计算/引用）**都不准写值**——把公式覆盖掉之后，这张表就再也不会自己更新了。
2. **系数与生产率一律从模板自身读，不准自己定、也不准外推。**
   生产率查不到就**停下来报缺**（见 6.6）。"用相近应用的数先顶上"是这个 skill 里最贵的错误：
   表看起来填完了，数字全是编的，而没有人能从成品里看出来。
3. **规模估算方法只走「估算功能点」这一条路**（`功能规模估算!C2` = `估算功能点`）。
   模板里「预估功能点」那一支引用的参数（`E15:E19`）**在模板中并不存在**，选它必报错（见 10.1）。
4. **"文档写的"与"推算的"必须分开。** 功能点来自需求文档（文档写的）；测试工时、页面描述、重用程度/修改类型里的"低/新增"缺省值，多半是**推算**。所有推算项要在交付说明里单独列出来，逐条带依据。
   **两类例外，必须原样照搬、不准"顺手统一"**：
   - `功能规模估算!C1`（应用名称）、参数表里的系统名与应用名 —— 用工作台需求分析的结果**逐字**填，见铁律 8；
   - 需求分析给出的功能点名 —— 它与 `requirement.json.featurePoints[].name` 一致，改名会让表与需求对不上。
5. **产出一律落 `Pipeline/方案/<开发人员>/cost/`，一个字都不写需求层。**
   不改 `requirement.json`、不改 `Pipeline/需求/` 下的任何文件（需求层的编辑权不属于方案阶段）。
6. **写完必须回读自检**（见 8.5）：公式保住了没有、有没有 `#VALUE!` / `#N/A` / `#REF!`。填完不回读，等于没填。
7. **模板本身是坏的（循环引用 + 参数缺失），必须把这两条写进交付说明。**
   不写，用户拿到一份全是 `#VALUE!` 的表会以为是 AI 填错了（见第 10 节）。
8. **除了"该你填的地方"，其它任何地方一律不动 —— 一个字、一个格式都不动。**
   该你填的只有三处：**文件名里的占位符**、`功能规模估算` 的明细区（第 5 节那几列）、
   `非功能规模估算` 的测试工时（**默认只动 `G6` 这一个单元格**，见 6.2）。
   其余单元格、公式、样式、批注、工作表顺序、行列结构全部保持原样。
9. **应用名称以工作台需求分析的结果为准，发现不一致只提醒、绝不修改。**
   工作台分析出的系统/应用名与模板 `功能规模估算!C1` 里已有的值对不上时，**停下来提醒用户**，
   把两边原值一起摆出来让他定；**你不改这一格**（见 4.1）。同理，参数表里的系统名/应用名也只读不写。

## 2. 先认模板：四张表、三个色区

### 2.1 模板形态

模板是一份 **Excel（.xlsx）**，四张工作表，除了"填写"和"读参数"之外**什么都不要动**（不要增删工作表、不要调整行列、不要改公式）：

| 工作表 | 作用 | 谁来写 |
|---|---|---|
| `功能规模估算` | 功能点计数项明细 → UFP → US → 合计 | 本 skill 填 |
| `非功能规模估算` | 非功能工作（测试支持、性能脚本、造数…）的人时 → 折算 FP | 本 skill 填 |
| `工作量估算` | 结果页：规模 → 生产率 → 工作量 → 角色分布 | **全是公式，一格都不填** |
| `模板使用说明&基础参数` | 色区说明、系数表、参数表、基准分布 | 只读（读系数与生产率） |

模板的固定坐标（**这些是契约，不要靠"找一找"**）：

| 位置 | 内容 |
|---|---|
| `功能规模估算!C1` | 应用名称（**查生产率用的键**） |
| `功能规模估算!C2` | 规模估算方法 → 本 skill 固定写 `估算功能点` |
| `功能规模估算!C3` | 未调整规模 `=L11`（公式，不填） |
| `功能规模估算!A5:N5` | 明细表表头 |
| `功能规模估算!A6:N8` | **明细示例区（3 行，结构一致）**：`A6=1/A7=2/A8=3`；`B=${系统}`、`C=${应用}`、`F=${功能点}`、`H=EQ`、`J=低`、`K=新增`；`I`/`L` 为**显式公式**。**新增行的模板行取 `A7` 这一行**（见 5.4） |
| `功能规模估算!A9:N10` | 预留空白明细行（只有样式，需自行补公式） |
| `功能规模估算!I11` / `L11` | `=SUM(I6:I9)` / `=SUM(L6:L9)`（公式，不填） |
| `功能规模估算` 的 4 条数据验证（**下拉框**） | `C1` ← 参数表系统名；`H` 列 ← `ILF,EIF,EI,EO,EQ`；`J` 列 ← `高,中,低`；`K` 列 ← `新增,修改,删除`；`M` 列 ← 问题归类。**`sqref` 区间是写死的，插行后必须一起扩展**（见 2.3 第 3 条） |
| `非功能规模估算!C1` | 所属软件产品 |
| `非功能规模估算!A6:I15` | 非功能明细（10 行）；**本次默认只填 `G6`**（测试工时），`H` 是折算公式 |
| `非功能规模估算!G16` / `H16` | 合计公式（不填） |
| `模板使用说明&基础参数!E5:E7` | 重用程度系数：高 `1/3`、中 `2/3`、低 `1` |
| `模板使用说明&基础参数!E10:E12` | 修改类型系数：新增 `1`、修改 `0.8`、删除 `0.2` |
| `模板使用说明&基础参数!E22:E26` | 估算功能点取值：ILF `10`、EIF `7`、EI `4`、EO `5`、EQ `4` |
| `模板使用说明&基础参数!C28:E307` | **参数表：软件系统名称 / 应用名称 / 开发生产率**（279 条，`_FilterDatabase` 也定义为 `C28:E307`） |
| `模板使用说明&基础参数!G21:K23` | 2023 年工作量分布基准：需求 `0.1328`、设计 `0.1266`、构建 `0.4143`、测试 `0.2253`、投产 `0.101` |

> 工作台侧还有一个**阶段模板**：`templates/方案/方案文档.md`（占位符语法 `{{path}}` / `{{#each}}` / `{{#if}}`）。
> 它和成本度量表模板**不是一回事**：前者是 Markdown 渲染模板，后者是 Excel 度量表。
> 第 7.3 节产出的「成本度量」Markdown 节是**给方案文档用**的素材，不要试图塞进 Excel。

### 2.2 色区（所有权）

- **深灰** = 模板固定部分，不得修改
- **浅灰** = 模板固定部分，必要时统一修改（本 skill **一律不改**）
- **绿色** = 自动计算或引用数据，不得修改
- **白色** = 需要填写/修改 —— **只有这里能写**

### 2.3 三个结构陷阱

1. **明细区只有 3 行示例（`6–8`）+ 2 行预留（`9–10`），合计写死在 `SUM(I6:I9)`。**
   功能点多于这些行时：**在 `10` 行下方插入行**，把合计行（原 `11` 行）**连同公式一起下移**，
   使 `SUM` 区间覆盖全部数据行。**不要**把多条功能点硬塞进一行、也**不要**另起一段写在合计行下面 ——
   两者都会让合计数字与实际不符，而这种错在成品里看不出来。`12` 行起是预留的空白行，插行时保留其单元格样式。
2. **非功能明细固定 10 行（`6–15`）**，`G16 = SUM(G6:G15)`。
   **本次默认只写 `G6` 一格**（见 6.2）；要写进 `G7:G15` 或插行，**先拿到用户确认**（见 6.4）。
3. **下拉框（数据验证）的区间是写死的 —— 插行后不会自动跟着长。**
   模板里 `H`（类别）、`J`（重用程度）、`K`（修改类型）、`M`（审核问题）四列都带下拉框，
   但它们的 `sqref` 是**固定区间**（形如 `H6:H8 H9:H10`）。只复制单元格、不扩展 `sqref`，
   新行就会是**没有下拉框的死格**——表面上填得进去，用户一改就只能手打、且不再受校验约束。
   **这属于"新增行没按现有规则来"，必须一起处理**（做法见 5.4）。

## 3. 输入：先读齐，再动手

按顺序读，读到什么记什么；**读不到就按第 4 节问，不要猜**。

| # | 要读的东西 | 从哪读 | 用来做什么 |
|---|---|---|---|
| 1 | 需求编号、标题、三个关键日期 | `docs/requirements/<编号>/requirement.json` | **文件名占位符**、交付说明抬头 |
| 2 | 功能点清单（`name`、`group`、`assignee`、`note`） | 同上 `featurePoints` | **明细区一行一条** + 文件名里的系统/应用名 |
| 3 | 需求正文（最新版本） | `Pipeline/需求/parsed/` 下版本号最大的那个 | 判 `H` 类别、判 `K` 修改类型、补 `F` 页面描述 |
| 4 | 本轮方案（若有） | `Pipeline/方案/<开发人员>/` 的 `draft.md`、`apis.json`、`pages.json` | 补页面描述（`pages.json` 直接就是页面清单）、估非功能与测试工时 |
| 5 | 模板 | 工作台根 `模板文件/任务软件开发成本度量表_[...].xlsx`；工作台里也可读 `templates/` 下同名的副本 | 开工底稿 + 系数/参数表（只读） |
| 6 | **工作台分析出的应用名** | `featurePoints[].group` 的第一/第二级，或正文里的系统应用名 | **与模板 `C1` 做一致性检查**（见 4.1），并用于文件名 |

> **开工前先给模板拍个指纹**：记下它的**字节数（或哈希）**与四个"出生特征"：
> ① 明细示例行占几行（当前是 `6–8`）；② 示例行的 `I`/`L` 是**显式公式**还是**共享公式**；
> ③ 4 条数据验证的 `sqref` 区间；④ 参数表最后一行（当前 `307`）。
> **模板是会被改的** —— 实测遇到过：用户补了示例行、字节数从 270092 变成 270416，
> 于是之前基于旧底稿生成的成品**当成就过期了**。指纹要写进 `cost.json` 的 `template` 并出现在交付说明里，
> 否则没人知道这份成品基于哪一版模板。
> **底稿一律以磁盘上"当前"的模板重新读取，不要复用上一次的解包结果。**

> **一个需求可能横跨多个系统。** 模板的 `C1` 只能填一个应用名称，参数表也是按"系统-应用"一行一条。
> 跨系统时**按系统拆成多份估算**（每份一张表、一个 `C1`），再在交付说明里给一张合计表。
> **不要**把两个系统的功能点混进一张表却只填一个 `C1` —— 生产率会整体用错。

## 4. 动手前必须先把这四件事定下来

### 4.1 应用名称一致性检查（发现不一致 → **只提醒，不修改**）

`功能规模估算!C1` 是查生产率的**精确匹配键**，所以它必须与工作台需求分析的结果一致。开工时对一次：

1. 读模板 `功能规模估算!C1` 的**现有值**（模板里往往残留着示例值，例如 `客户关系管理后端服务`）。
2. 读工作台需求分析的结果：`requirement.json.featurePoints[].group` 拆出的系统/应用名、需求正文里的系统应用名。
3. 两边**逐字比对**（去首尾空白，但不要忽略中间空格与全半角差异）：

| 情形 | 怎么办 |
|---|---|
| **一致** | 直接用，继续往下做 |
| **不一致** | **停下来提醒用户**，把两边原值摆出来，**由用户决定以谁为准** |
| 模板值**为空** | 用工作台分析的结果填上（这是"该你填的地方"） |
| 模板值**是示例值**（如 `客户关系管理后端服务`、`${应用}` 未替换） | 同"不一致"处理：提醒用户确认后再填 |

**不一致时你只做三件事**：① 原样报出模板值；② 原样报出工作台分析值；
③ 给出参数表 `C28:E307` 里能命中的候选行，让用户挑。**不要自己改 `C1`**，也不要为了"让 VLOOKUP 能查到"而去改工作表里的应用名 ——
那是绕过提醒，不是解决问题。这次的不一致必须同时写进交付说明的「待补项」和最终报告。

### 4.2 文件名：把占位符换成需求分析的实际值

文件名按模板命名：`任务软件开发成本度量表_[${需求编号}]${需求描述]_${系统}-${应用}.xlsx`。
四个占位符的取值来源**只有一个：需求分析的结果**（`requirement.json` + 正文），不要自己命名。

| 占位符 | 取值 | 来源 |
|---|---|---|
| `${需求编号}` | 完整需求编号 | `requirement.json.id`，形如 `XQ20260918-0009` |
| `${需求描述}` | 需求标题/简述 | `requirement.json.title` |
| `${系统}` | 系统名 | `featurePoints[].group` 的第一级，或正文里的系统名（与 4.1 认定的应用名同源） |
| `${应用}` | 应用名 | 与 4.1 一致的那个应用名 |

替换后**去掉包裹的方括号 `[ ]`**，并去掉文件名不安全字符（`/ \ : * ? " < > |`）与首尾空白：

```
任务软件开发成本度量表_XQ20260918-0009_客户经营信息优化_CRM客户关系管理系统-客户关系管理后端服务.xlsx
```

**同时要替换文件名之外的两处易漏点**（这是最容易漏的一步）：

1. **单元格里残留的占位符**：`${系统}` / `${应用}` / `${功能点}` / `${测试工时}` —— 逐个定位并替换
   （`${功能点}` 与 `${测试工时}` 分别在两张明细表的第 6 行示例行里，`${系统}`/`${应用}` 在功能明细行）。
2. **文件名与工作表内的应用名必须一致**：不要出现"文件名写 A、`C1` 写 B"。

**注意不要碰工作表名与公式**：公式里的 `'模板使用说明&基础参数'` 是**工作表引用**，不是占位符，
一个字都不能动。

> 交付前扫一遍全表：`${` 必须 **0 命中**（见 8.5）。

### 4.3 三个"读不出来才问"的输入

只有这三项**读不出来**才问；读得出来就直接填，不要为了"确认一下"打断流程。

| # | 输入 | 为什么不能猜 | 取不到时的默认 |
|---|---|---|---|
| 1 | **应用名称**（`C1`） | 它是查生产率的精确匹配键；写错不会报错，只会静默用错生产率 | 按 4.1 处理（不一致就提醒，不自作主张） |
| 2 | **测试工时**（`G6` 的人时） | 模板里这格是 `${测试工时}` 占位符，**需求文档里通常没有这个数** | 按 6.3 的默认口径：**开发工时 ÷ 3，且取 4 的倍数**，只写 `G6`，标「推算」 |
| 3 | **跨系统的分摊**（仅当需求跨系统） | 一个功能点算在哪个系统下只有业务能定 | 按功能点 `group` 就近归属，逐条标注「推算」 |

**问法**：选项要给出你推荐的取值 + 依据，让用户点一下就能定，而不是丢一个空问题。

> **无人可问（无人值守 / 只读模式）**：把问题**逐条原样写出来**，给出默认假设下会怎么继续，
> 并**显式标注哪些结论建立在默认假设上**；只读时**不写盘**，把 `cost.json` 与交付说明
> **以文本形式交回调用方**，并说明"按纪律未落盘"。

### 4.4 只准动这三处（硬规则）

| 该你动 | 具体位置 |
|---|---|
| ① 文件名占位符 | 输出文件名 + 单元格里残留的 `${...}`（见 4.2） |
| ② 功能规模估算明细 | `功能规模估算` 的 `A` / `B` / `C` / `D` / `E` / `F` / `G` / `H` / `J` / `K` / `N` 列（见第 5 节）<br>**含"按用户新增一行的规则"扩容**：克隆示例行、重编号（含公式正文裸引用）、**扩展 `H`/`J`/`K`/`M` 四条下拉框的 `sqref`**、合计行下移（见 5.4） |
| ③ 非功能规模估算测试工时 | `非功能规模估算` **默认只动 `G6` 一个单元格**（见 6.3） |

> **③ 是"一格"的授权，不是"一列"的授权。** 默认只写 `G6`；
> `G7:G15`、`F` 列描述、`B`/`C` 列系统应用名、`G16` 合计、以及"插行"这类结构改动，
> **一律要用户明确确认之后才能动**（见 6.3）。

**除此之外一律不可修改** —— 包括但不限于：公式列（`I` `L` `I11` `L11` `H` `G16` `H16`）、
`工作量估算` 整表、`模板使用说明&基础参数` 整表、所有单元格的颜色/批注/格式、
工作表名称与顺序、行列结构（除第 5 节说明的**必要插行**外）。
**拿不准某一格该不该动时，默认不动，并在报告里问一句。**

## 5. 填「功能规模估算」——按功能点补页面

**核心动作只有一句：把需求分析出的功能点，逐条展开成表里的明细行，并把"页面/功能项"那一列补出来。**
一行一个功能点，不合并、不漏填、不新增表里没有来源的行。

### 5.1 列怎么填（表头自己写明了要什么，照着填）

| 列 | 表头 | 填什么 | 必须动吗 |
|---|---|---|---|
| `A` | 编号 | `1,2,3…` 连续 | ✅ |
| `B` | 一级模块 | **系统名**（与 4.1 认定的应用名同源），逐字一致 | ✅ |
| `C` | 二级模块 | **应用名**，一张表内所有行同属一个应用 | ✅ |
| `D` | 三级模块 | **通常不写**（留空） | ⬜ |
| `E` | 四级模块 | **通常不写**（留空） | ⬜ |
| `F` | **功能项描述** | **本次要补的"页面"**：该功能点对应的页面/功能名 + 一句话说明它在页面上做什么 | ✅ |
| `G` | 功能点计数项名称 | 需求分析给出的**功能点名**，与 `featurePoints[].name` 逐字一致 | ✅ |
| `H` | **类别** | `ILF` / `EIF` / `EI` / `EO` / `EQ`，**通常为 `EQ`**（判据见 5.2） | ✅ |
| `I` | UFP | **公式列，不填** | ⛔ |
| `J` | 重用程度 | `高` / `中` / `低`，缺省 `低` | ✅ |
| `K` | **修改类型** | `新增` / `修改` / `删除`，**按功能点判**（判据见 5.3） | ✅ |
| `L` | US | **公式列，不填** | ⛔ |
| `M` | 审核问题 | 留空 | ⬜ |
| `N` | 备注 | 判定依据，例如「文档 3.2」「按 `group` 归到客户主数据」 | ✅ |

**`D`/`E` 留空是默认口径**：需求分析的 `group` 只到"分块 → 功能点"两级，
硬拆三级/四级只会造出文档里不存在的层级。除非用户明确要求按模块分层，否则一律留空。

### 5.2 类别怎么判（`H` 列）——**默认 `EQ`**

这类以"查/看/列表/详情"为主的页面功能，**绝大多数是 `EQ`**。只有明显不是查询时才改：

| 类别 | 什么时候用 | 你的默认 |
|---|---|---|
| `EQ` 外部查询 | 查询、检索、列表、详情查看 —— **不改变状态、不含派生计算** | ✅ **默认值** |
| `EI` 外部输入 | 从页面进来、**改变系统状态**的（新增/修改/删除/提交/审批/导入） | 功能点明显是"建档/提交/修改/删除"时 |
| `EO` 外部输出 | 出去且**带派生数据**的（统计汇总、指标计算、导出且列经过计算） | 功能点明确是"统计/汇总/导出计算列"时 |
| `ILF` 内部逻辑文件 | 本系统自己**维护**的一组数据 | 极少数：功能点就是要建一整张业务表 |
| `EIF` 外部接口文件 | 本系统**只读引用**、别的系统维护的数据 | 极少数：功能点就是引外部系统数据 |

**判错的两个高发点**：

- 一条功能点里"既查又改" → **只填一个类别**，按主要动作判；确实两件事就拆成两条功能点（EQ + EI）。
- 列表页带"合计行/统计卡片" → 那是派生数据，**归 `EO`**；纯筛选列表才是 `EQ`。
- 拿不准时去对一眼模板自带的计数问题归类 `模板使用说明&基础参数!G29:H48`（常见误判清单）。

**每一条把类别判成非 `EQ` 的，都要在 `N` 列写一句依据**（否则复核的人只会看到一堆"本该是 EQ 却不是"）。

### 5.3 修改类型怎么判（`K` 列）

拿功能点本身 + 需求正文一起判，**不要一律填"新增"**：

| 值 | 判据 |
|---|---|
| `修改` | 需求正文里这条是**在既有页面/功能上改**（加字段、加筛选条件、改展示口径、优化交互）；或该功能点能对上一版文档/既有工程里已实现的能力 |
| `删除` | 明确要**移除**某个页面/功能/字段（含"底色 + 删除线"这类删除标记） |
| `新增` | 正文里**找不到原功能**、是本期新做的页面/功能 |

- 判不出来时**默认 `新增`**（这是模板批注里写明的缺省值），但要**在 `N` 列标注「按缺省判新增，待复核」**。
- 不要因为"怕填错"就全填"新增" —— 本 skill 明确要求按功能点逐条判，理由见 8.1 的自检项。

### 5.4 行不够时：按"用户在页面上新增一行"的规则来加

> **这是最容易做错、也最容易被忽略的一步。** 判据很简单：
> **加完之后，新行与模板里的示例行必须"用起来一模一样"** ——
> 单元格里该有公式的有公式、该有下拉框的有下拉框、该有的样式都在。
> 只把值写进去、公式和下拉框留空，等于交付了一堆"死格"：用户想改的时候改不动、
> 也拿不到校验保护。

功能点通常远多于模板的示例行（默认 `6–8` 三行示例 + `9–10` 两行预留），所以必须**主动复制行**。

#### 5.4.1 正确的新增行＝四件事，缺一件都不算完成

| # | 动作 | 判据（做完怎么验证） |
|---|---|---|
| ① | **取模板行**：以 `A7`（示例行，含 `I`/`L` 的**显式公式**与全部样式）为准，克隆出需要的行数 | 新行的 `I`/`L` 有公式，不是空值 |
| ② | **重编号**：行号与行内**所有单元格引用**一起改成新行号（`I7`→`I12`，公式里的 `H7`/`J7`/`K7`/`I7`/`L7` 同步） | 公式引用的是**自己这一行**，不是第 7 行 |
| ③ | **扩展数据验证（下拉框）**：把 `H`/`J`/`K`/`M` 四条 `dataValidation` 的 `sqref` 扩到覆盖全部明细行 | 在新行上点 `H`/`J`/`K` 能**弹出下拉框** |
| ④ | **下移合计行**：合计行连同公式下移，`SUM` 区间覆盖全部数据行；`mergeCell`（形如 `J11:K11`）跟着下移 | 合计公式区间 = 首行:末行 |

顺序也重要：**先 ①②③④ 把"行"造对，最后才填值**。反过来（先填值再补结构）很容易漏掉第 ③ 步。

#### 5.4.2 克隆哪一行

- **用 `A7` 那一行**：它的 `I`/`L` 是**显式公式**（写死 `H7`/`J7`…），克隆后按新行号替换即可；
- **不要用 `A6`**：`A6` 是首行，可能与 `A7` 在缓存值/格式细节上不完全一致；用示例中间行更稳；
- `A9`/`A10` 是**只有样式、没有公式**的预留行 —— 它们只能提供样式，公式必须自己注入
  （历史上这里踩过坑：模板 6–9 行的 `I`/`L` 曾经是**共享公式**，只有主格带 `<f>`、其余是"从属无公式"，
  克隆出来全是空公式。**判断依据永远是"克隆完去读那一格有没有 `<f>`"，不要假设**）。

#### 5.4.3 公式必须逐格核对，不要相信"复制就会带走"

克隆完在**写盘前**跑一遍自检（硬断言，不通过就不要交）：

```
对每一个明细行 r（首行 .. 末行）：
  该行的 I、L 两个单元格都必须含 <f>，且公式里的行号 == r
对每一条 dataValidation：
  扩展后的 sqref 必须覆盖 首行..末行
对合计行：
  SUM 区间 == I{首行}:I{末行} / L{首行}:L{末行}
```

#### 5.4.4 不要做的事

- **不要**把多条功能点挤进一行；
- **不要**把多出来的行写到合计行**下面**（合计数字会与实际不符，而这种错在成品里看不出来）；
- **不要**只改 `sqref` 里的列而不落行号（写成 `H:H` 这类整列区间看着"能用"，但会把表头、
  合计行也纳入校验，属于擅自改模板结构）；
- **不要**因为"下拉框还没长出来"就改成手填文本 —— 那是把结构问题掩盖成数据问题。

## 6. 填「非功能规模估算」

### 6.1 什么算非功能

只收**开发要额外投入、又不产生功能点**的活，典型四类：

1. 性能工作（压测脚本、指标调优、容量验证）
2. 测试支持（造数、环境准备、联调支持）
3. 安全与合规加固（等保整改、脱敏、审计日志补全）
4. 数据迁移/初始化（一次性脚本、数据核对）

**不要**把功能开发塞进来 —— 那已经算在功能点里了，重复计算会让规模虚高。

### 6.2 只准动 `G6` 一格

**默认动作只有一个：把测试工时写进 `非功能规模估算!G6`。** 其余单元格一律不动。

| 单元格 | 默认 | 为什么 |
|---|---|---|
| `G6` 预估工作量(人时) | ✅ **唯一要填的** | 模板里它是 `${测试工时}` 占位符，就是留给"简单评估测试时长"的那一格 |
| `F6` 非功能工作内容描述 | ⛔ 不动 | 模板已写好「测试支持（包括性能测试脚本编写，造数）」，不需要重写 |
| `B6` / `C6` 一级/二级模块 | ⛔ 不动 | 与需求分析结果的一致性检查归 4.1，不是这里顺手改的理由 |
| `H6` 折算功能点 | ⛔ 不动 | 公式（`= G6 / 工作量估算!B$3`） |
| `G7:G15`、`F7:F15` 其余行 | ⛔ 不动 | 本次是**简单评估**，不铺开写非功能明细 |
| `G16` / `H16` 合计 | ⛔ 不动 | 公式 |

**为什么只动一格**：这次是**简单评估测试时长**，不是把非功能工作逐条盘点。
`G6` 就是模板留给这一项的那一格（`${测试工时}` 占位符），一行写完、改动面最小、便于复核；
一旦铺开写进 `G7:G15`，`H6:H15` 的折算、`G16`/`H16` 的合计、结果页的加权口径都会跟着变，
"简单评估"就变成了另一次规模盘点。

> **需要动 `G6` 之外的单元格时（例如要给多条非功能工作分别填工时、要插行、要改模块名），
> 必须先问用户、拿到明确确认再动**，并在报告里写清"动了哪几格、为什么、谁确认的"。
> **没确认就不动** —— 需要更多明细时，把建议写在交付说明里，让用户决定，而不是先改了再解释。

### 6.3 测试工时怎么算：开发工时 ÷ 3，且取 4 的倍数

规则只有两条：**开发时长的三分之一**、**且是 4 的倍数**。

```
1) 先算出该应用/需求的「开发工时」—— 用功能规模估算的合计 US（L11）乘生产率、再乘行业开发占比：
   开发工时(人时) ≈ 功能规模合计(US) × 生产率(人时/FP) × 0.64078
   （0.64078 = 模板 工作量估算!C10 的开发工作占比，见 6.5）
2) 测试工时 = round(开发工时 ÷ 3 ÷ 4) × 4      ← 先除 3，再就近取 4 的倍数
3) 填进 G6（人时），并在交付说明的「推算项」里写清算式
```

**要落实到位的几点**：

- **必须是 4 的倍数**（`12` `16` `20` `24`…），填完自己整除校验一遍；
- **不是**"凑一个好看的整数"，也不是照抄别的需求的数；
- 开发工时本身是**推算**的，所以测试工时**连同算式一起**标「推算」；
- 需求文档或用户**明确给了**测试工时时，**以给的为准**（此时不再套默认口径），但仍要满足 4 的倍数；
  不满足就取最近的 4 的倍数并说明调整了多少；
- 只有**一格**要填，所以 `cost.json` 里记一条 `nonFunctional` 就够，不要为它造出多行明细。

### 6.4 需要超过一格时：先确认，再动手

**默认不做**。以下情形都属于"要动 `G6` 之外"，一律先问用户：

- 非功能工作不止"测试支持"一条，想分行写进 `G7:G15`；
- 行数不够、想插行或下移 `G16` 合计；
- 想改 `F6` 的描述文字、`B6`/`C6` 的系统应用名。

用户确认后按 5.4 的同一套做法操作（插行要沿用原行样式、合计区间要覆盖全部数据行），
并在报告里单独列出这几处改动与确认来源。

### 6.5 结果页怎么算（只读，用于自检、算测试工时与写报告）

```
总规模(FP) = 功能规模!L11 + 非功能规模!C3
生产率      = 参数表命中值        下限 = ×0.8   上限 = ×1.2      （人时/FP）
开发工作量  = 总规模 × 生产率 ÷ 8                                 （人天）
角色分布    = 按 G21:K23 基准重新组合（见下）
```

2023 基准的重组口径（模板 `工作量估算!B10:E10` 的公式）：

| 角色 | 系数 | 由基准怎么来 |
|---|---|---|
| BA 工作 | `0.05312` | `需求 0.1328 × 0.4` |
| 开发工作 | `0.64078` | `需求×0.6 + 设计 + 构建 + 投产×0.2` |
| 测试工作 | `0.2556` | `测试 + 投产×0.3` |
| 运维工作 | `0.0505` | `投产×0.5` |

四个系数合计 `1.0`。**这是模板的固定口径，不要自己重算百分比**（重算出来的数会在小数末位上和表里不一致）。
注意：这里的 `0.2556` 是**行业基准里的测试占比**，与 6.3 那个"开发工时 ÷ 3"的**填写口径**是两件事，
不要相互替换。

### 6.6 生产率：精确匹配，查不到就停

1. 用 **`功能规模估算!C1`（应用名称）** 在 `模板使用说明&基础参数!C28:E307` 里做 **exact match**
   （VLOOKUP 第 4 参数 = `0`），比较时**去首尾空白**，但**不要**忽略中间的空格与全半角差异 ——
   键值必须逐字一致。
2. **命中一行** → 取该行的 `E` 列（开发生产率，单位 **人时/FP**）。
3. **命中多行**（同名应用）→ **停下来问用户**要用哪一行（参数表里同名不同系统确实存在）。
4. **查不到** → **停下来报缺**：把 `C1` 的原值、参数表里最接近的几条候选一起列出来，让用户定。
   **绝不允许**用"相近应用"的生产率顶上、也不允许取平均值 —— 这是本 skill 最贵的一类错误。
5. 顺手核对 VLOOKUP 的**区间与数据范围是否一致**：模板公式写的是 `D29:E568`，
   而数据只到 `E307`（见 10.2）。命中在范围内就继续，但要把这条记进交付说明。

## 10. 模板已知缺陷与规避（必读，必写入交付说明）

### 10.1 循环引用（会让结果页整片失效）

- `工作量估算!B1 = 功能规模!L11 + 非功能!C3`
- `非功能!C3 = H16 = SUM(H6:H15)`，而 `H6 = G6 / 工作量估算!B$3`（**B$3 是靠 B1 才定出来的生产率**）

于是：非功能折算依赖生产率 → 生产率依赖总规模 → 总规模依赖非功能折算。Excel 解不开，
`B1`、`B5:B7`、`B11:E11` 全部落成 `#VALUE!`。

**本 skill 的规避**：**不在模板里"修"这个引用**（那是改公式，违反色区规则）。
做法是**自己按 6.5 的口径独立算一遍**，把结果写进 `cost.json` 与 `成本度量.md`；
Excel 里如实保留 `#VALUE!`，并在交付说明里写清"这是模板自带问题，不是本次填写造成的"。
若用户明确要求"表里也要出数"，**单独确认**后再把 `H6` 的分母改成固定值 —— 那是一次**改公式**的动作，
必须让用户点头，并记进交付说明。

### 10.2 VLOOKUP 区间超出数据范围

公式写 `D29:E568`，参数数据只到 `E307`（第 308 行起为空）。当前命中靠"落在范围内"侥幸成立；
若手工在参数表尾部补过行，**必须先确认数据边界再改公式区间**，否则会把空行的 `0` 当成生产率。

### 10.3 `预估功能点` 分支的参数缺失

`功能规模估算!I` 列公式在 `C2="预估功能点"` 时引用 `模板使用说明&基础参数!E15:E19`，
**这五行在模板里根本不存在**。所以：

- 本 skill **固定走 `估算功能点`**（第 1 节铁律 3）；
- 用户若坚持要"预估功能点"口径，**先补出 `E15:E19` 五个取值并让用户确认**，再往下做。

### 10.4 明细区容量小

功能明细模板只有 **3 行示例（`6–8`）+ 2 行预留（`9–10`）**，非功能只有 10 行，而合计公式的区间是写死的。
**加行是本 skill 的常规动作**，但加行容易带走格式、漏掉合计区间、**尤其容易漏掉下拉框的 `sqref`** ——
所以 5.4 那套"四件事"和 8.3 的两条硬检查项都不能跳。
